# 0028: Two-step sign-in exempts only sample workspaces (`isSampleRow`); stray promise rejections are logged, not fatal

- Status: proposed (security-reviewer accepts)
- Type: security

## Context
Decision 0025 wrote the two-step exemption as `companies.demo = true`, but the codebase's sample-workspace test is `isSampleRow` (`demoOwnerUserId` set or `settings.demoRetiredAt`, `src/modules/tenancy/demo-flag.ts`). The seeded Desert Bloom has `demo = true` without being a sample workspace, so its owner and admin were never required (backlog B-299). Decision 0029 (product, accepted 2026-10-09) settles the product side: the seeded shop follows the real rule, no seed bypass. Separately, the sign-in after-hook fired `notifyLocked(email)` with `void` and no `.catch`, and neither the API nor the worker had an `unhandledRejection` handler, so a DB error while sending the lock email would end the API process (Node 24 default), and the drizzle error text quotes the query params, the email among them (B-297, `waves/28/reviews/T-28-2-reviewer-r1.md` notes 1-2). Links: card T-29-2, decisions 0025 and 0029, plan review `waves/29/reviews/plan-architect.md` item 7. Built by backend-foundation; reviewed by reviewer and security-reviewer.

## Decision
1. **Exemption.** `MfaMembership` carries `sample: boolean` = `isSampleRow(row)`, selected inside the same membership join (`sampleColumns` + `withSampleFlag` in `src/lib/mfa.ts`; used by `activeMemberships`, `src/api/context.ts` and `tenancy.demo` switch). Required = an active `owner`/`admin` membership in any non-vendor org that is not a sample workspace. `companies.demo` alone never exempts. `isMfaRequired(memberships)` keeps its signature. Grace length (7 days), exempt procedures and lockout values are unchanged.
2. **No grace restart when the rule flips.** `users.mfa_grace_starts_at` defaults to user creation, so a dev DB seeded more than 7 days ago blocks `owner@` and `admin@` at once: reseed or enroll (decision 0029 item 3).
3. **Reactivation is the one allowed restart.** Reactivating a deactivated owner/admin through `setMemberStatus` restarts the grace when the user was not required before and `users.mfa_required_since` is null (the S-58 once-per-user rule, decision 0025). Deactivating a required user sets `mfa_required_since`, so a later reactivation, or any deactivate/reactivate cycle after the first restart, keeps the old deadline. No code change was needed.
4. **Lock email failures.** The after-hook calls `notifyLocked(email).catch(...)` and logs `"lock email failed"` at error with `errorKind(err)` only: the error class and Postgres code, never the message. The sign-in answer does not change. SMTP failures were already caught inside `sendAuthMail`.
5. **Process handlers.** The API (`src/api/server.ts`) and worker (`src/worker/index.ts`) register `process.on("unhandledRejection")`, which logs `"unhandled rejection"` at error through `logger` (`errorData`) and keeps running. `uncaughtException` keeps Node's default (log and exit; the task restarts), because after a synchronous throw the process state is unknown.

## Consequences
- The owner sees the real banner and block on the seeded shop; sample workspaces stay frictionless. Any test suite or gate on a fresh seed is unaffected (the deadline is 7 days out); a stale local DB needs `db:reset` + seed or enrollment (runbook and demo guide, docs-writer).
- A stray rejection no longer crashes the API or worker, but it is only as visible as the error log: alerting on `"unhandled rejection"` is platform-sre's follow-up when alerts exist. The generic handler logs `errorData` (message and dev stack), the same as `job failed`; the S-29 redaction gap for drizzle params applies to both.
- Enforced by `src/lib/account-security.test.ts` (isSampleRow cases: live, retired, seeded `demo = true`; reactivation restarts once) and `src/lib/account-lockout-notify.test.ts` (a rejecting `notifyLocked`: same 401, logged by kind, no email in logs, no unhandled rejection). Decision 0025's body stays unchanged; this decision narrows its exemption wording.
