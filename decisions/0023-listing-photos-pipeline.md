# 0023: Listing photos pipeline: `photos` contract, design lock, disclosures, approval, credits, queue

- Status: accepted (2026-10-02)
- Type: architecture

## Context
- Decision 0022 (owner) fixed the product rule: an image model may draw scenes, garments and people around the shop's design; the design's pixels are only ever composited by `invai-imaging`. This ADR is the technical reference 0022 names: the contract shapes (`invai-contracts` 0.12.0, `src/contract/photos.ts`, `src/schemas/photos.ts`) and the rules every builder follows in waves 26 (phase A, templates) and 27 (phase B, AI scenes and Shopify push).
- Evidence and constraints: spec `specs/listing-photos.md`; wave plans `waves/26/wave.md`, `waves/27/wave.md` (agreed interfaces); plan review `waves/26/reviews/plan-architect-r1.md` (items 1, 3–8); backend facts: `bucketFor` routes only `ai.*` to the `ai` rate bucket (`invai-backend/src/api/orpc.ts:186`), `ai_credit_ledger` has no unique key (`src/ai/credits.ts:63`), `createDrafts` enqueues with `afterCommit` and `generateDraft` runs with no transaction (`modules/ai/service.ts:273,450`), `exportCsv` writes no image URLs (`service.ts:771,854`), `listings.channelListingId` holds Shopify's legacy product id (`db/schema/channels.ts:96`, `integrations/channels/shopify/common.ts:251`). OpenAI documents GPT Image masks as prompt guidance only, with fixed output sizes 1024², 1536×1024, 1024×1536.
- Card T-26-1 (architect). Reviewed by reviewer (opus), backend-foundation, web-engineer.

## Decision
1. **Design lock.** Design pixels enter one process only: `invai-imaging` (`/photo/render`, `/photo/scene-composite`). No request to any image model carries design bytes, a design URL, or an instruction to draw, redraw or alter the design. Phase B sends the provider a blank, masked base (`/photo/scene-base`) and composites afterward. The analysis route (vision) receives the design's small preview to describe it, never to generate from it.
2. **Two-check drift rule (phase B).** Every composite runs check 1 `region_changed` (garment outline aligned: the output is registered to the base and an edge map in a ring around the print box is compared; the base's blank print-box pixels are restored before compositing, because the provider may re-render the whole frame) and check 2 `design_drift` (SSIM of the printed region against the source design, reported as `PhotoImage.designLockScore`). Thresholds live in imaging and are reported with each result (`checks.regionUnchangedScore`, `designLockScore`). A failed check regenerates once; a second failure marks the image `failed` with that code, never approvable, and the shop is not charged for it. Provider-size output is upscaled to the preset size; the upscale is documented in the image's `widthPx/heightPx`.
3. **Disclosure follows the source.** `PhotoImage.aiGenerated` is true only for `source = ai_scene`. `containsSyntheticPerson` is decided from the requested scene kind (`SceneSuggestion.containsPerson`), never from inspecting the output; every such image gets XMP `contains-synthetic-performer`. A drawn template (`drawnTemplate = true`) is an illustration, not AI: no AI disclosure, but Amazon main slots get the `illustration_not_photo` check. Attaching any AI image to a draft sets `ListingDraft.imageDisclosures.aiGenerated` (Etsy AI-use disclosure, a separate `IMAGE_AI_DISCLOSURE` sentence in the Etsy export, never `AI_DISCLOSURE`) and `syntheticPerformer` when a person is present; once set, later template attaches never clear them. Image disclosures live in their own draft column `image_disclosures`, not in `content` (which `regenerateDraft` rebuilds).
4. **Approval before anything leaves.** Only images in `approved` (`PHOTO_EXPORTABLE_STATUSES`) may be zipped, attached or pushed. Bulk-upload CSVs carry no image URLs (S3 keys are not public), so images leave InvAI only by `exportZip` or `pushToShopify`; both exclude unapproved ids with `PhotoExclusion.reason`, and refuse with `BAD_REQUEST {reason: "not_approved", count}` when nothing is approved. Signed URLs appear only in `getSet` (company-prefix keys only) and the list's one `leadImageUrl`.
5. **Credits.** The charged unit is a `PhotoComposition` (garment × view × color for templates, one AI scene for lifestyle): `PHOTO_TEMPLATE_CREDITS = 1`, `PHOTO_SCENE_CREDITS = 10` (OI-25; the owner may change them). Channel derivatives are free. Charge guard: `SELECT … FOR UPDATE` on the composition row, charge only when `charged_at IS NULL`, set it in the same transaction; ledger `ref = {type: "photo_composition" | "photo_scene", id}`; kinds `photo_image`, `photo_scene` appended to `CREDIT_KINDS`. `createSet` refuses with `CREDITS_EXHAUSTED` before anything is enqueued; phase B also checks `IMAGE_DAILY_CAP_REACHED` (per-shop daily scene cap) and `AI_SPEND_CAP_REACHED` first.
6. **Everything heavy runs on the queue.** `analyzeDesign` returns the cached analysis or enqueues a job on the `ai` queue and answers `{status: "pending", jobId}`; no transaction is held across a model call (precedent: `createDrafts`/`generateDraft`). `createSet` only creates rows and enqueues one `render`-queue job per composition at a lower priority than gang-sheet compose; zip and Shopify push are jobs; the web polls `getSet` or listens to realtime `photo_set.updated`.
7. **`productRef` is a backend listing.** `pushToShopify.productRef = {listingId}` points at a `listings` row of the same company, the same `connectionId` and channel `shopify`; the backend maps `channelListingId` to `gid://shopify/Product/<id>`. `pushTargets` lists them, this design's first. Any other channel stays zip-only until its adapter and marketplace approval exist.
8. **Procedures, methods and rate buckets** (backend `bucketFor` grants, T-26-4): `analyzeDesign` POST `/photos/analyze` → `ai`; `estimate` POST `/photos/estimate` → `reads` (NON_GET_READS); `createSet` POST `/photos/sets` → `ai`; `listSets` GET `/photos/sets` → `reads`; `getSet` GET `/photos/sets/{id}` → `reads`; `reviewImages` POST `/photos/sets/{setId}/review` → `writes`; `exportZip` POST `/photos/sets/{setId}/zip` → `writes`; `attachToDraft` POST `/photos/sets/{setId}/attach` → `writes`; `pushTargets` GET `/photos/push-targets` → `reads`; `pushToShopify` POST `/photos/sets/{setId}/push` → `ai`. Permissions `photos.read` / `photos.manage`: owner, admin, office, designer; `auth: user` only.
9. **Retention.** Raw provider scenes (before compositing) are kept 7 days for drift review, then purged; zips 30 days after `builtAt`, rebuilt on demand; rendered images follow the design (deleted with it). Enforced by the photos module's purge job (T-27-3).

## Consequences
- Easier: wave 27 needs no contract change; web, backend and ai build against one shape set with the checks, disclosure flags and credit unit already named; a tablet or browser one version behind keeps parsing (`imageDisclosures` optional, enum values appended).
- Harder: phase B must implement real registration and SSIM in imaging and justify thresholds; the backend must keep the composition-level charge guard and the three-step job pattern.
- Follow-ups: backend grants for `bucketFor`/`buckets.test.ts` (T-26-4); `CREDIT_KINDS` mirror and `image_disclosures` column (T-26-3); web `keysForEvent` case for `photo_set.updated` and `creditKind.photo_image/photo_scene` labels (T-26-5); files `canReadKind` mapping for photo keys to `photos.read` (backlog, files owner); compliance re-verifies preset numbers and disclosure wording before a real shop uses it.
- Enforcement: `invai-contracts/src/photos.test.ts` (routes, permissions, errors, transitions, ratios, enum tails, version); backend `authz.test.ts` walks the permissions; `buckets.test.ts` fails on an unclassified non-GET read.
