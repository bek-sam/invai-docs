# Read before change

Every line you write matches the library version actually installed and the code that already exists, not what
you remember.

## When to use
- Before the first edit on any card (after `task-intake`).
- Before calling any library API you haven't read in this repo today.
- When a type error, runtime error or test failure suggests the API differs from what you expected.

## Steps
1. **Read the surrounding code first.**
   - The repo README and the module you touch (`invai-backend/src/modules/README.md` for backend layout).
   - How the same thing is already done: `grep -rn "<similar thing>" <repo>/src` and copy that pattern.
     Examples: `withTenant(` in `src/db/client.ts`, `defineJob(` in `src/lib/queues.ts`, `emit(` in
     `src/lib/outbox.ts`, `isCompanyKey(` in `src/lib/s3.ts`, `assertCredits(` in `src/ai/credits.ts`.
   - The tests next to it (`*.test.ts`) and the fixtures in `invai-backend/src/test/fixtures.ts`.
   - `invai-docs/build/architecture-as-built.md` for how the system really works (it differs from
     `architecture.md` in places).
2. **Check the installed version,** not the one in your head:
   ```
   node -p "require('./node_modules/<pkg>/package.json').version"   # run inside the repo
   ```
   Python (imaging): `uv pip show <pkg>` inside `invai-imaging`.
3. **Read the real API in `node_modules`** for anything on the list below, or anything you are unsure of. Type
   declarations are the truth: open the `.d.ts` / `.d.mts` file for the export you use. `node_modules` entries
   are pnpm symlinks, so use `find -L` or open the path directly.
4. **If the local files aren't enough,** read the official docs for that exact major version. Say in your
   report which source you used.
5. **Re-read after a failure.** When the typechecker disagrees with you, the typechecker is right about the
   installed version. Don't cast (`as any`, `@ts-expect-error`) your way past it.

## Rules
- MUST check `node_modules` or the official docs for any API on the list before using it. This is the v1
  lesson "code written against the wrong library API" (`team/lessons.md`).
- MUST follow the pattern already used in the repo unless the card says to change it.
- MUST NOT upgrade or add a dependency to make an API you remember work. A new dependency needs a reason in
  your report and passes `dependency-and-container-audit` review.
- MUST NOT silence the typechecker or linter (`as any`, `@ts-ignore`, `biome-ignore`) to fit a remembered API.
- Use `export PATH="$HOME/.local/share/pnpm/bin:$HOME/.local/share/pnpm:$PATH"` first in every shell; the
  system Node 22 gives wrong answers.

## Done when
- For each library API you used, you can name the file in `node_modules` (or the doc URL and version) you
  checked.
- Your code follows an existing pattern in the repo, or your report says why not.
- `pnpm typecheck` passes with no new casts or suppressions.
