## Lessons that apply to you
- 2026-09-26 W8: Never `git stash`, `reset` or `checkout --` in a shared tree; compare in your own worktree at the base commit.
- 2026-09-26 W8: Don't push. Only the tech lead pushes, after the gate (a builder once pushed 44 ungated commits).
- 2026-09-25 W3: Shared files: stage only your hunks (`git add -p` / `git apply --cached`), check `git diff --cached`, then commit.
- 2026-09-24 W2: Kill only PIDs you started (`lsof -ti :<your port>`); never `pkill`/`killall`.
- 2026-09-25 W6/7: Never run `pnpm` inside a worktree; call `node_modules/.bin/*` directly. Never re-link shared `node_modules`.
- 2026-09-25 W3: Poll long jobs inside your turn with short sleeps; don't end your turn to wait.
- 2026-09-24 v1: Check the installed library API in `node_modules` before writing code (oRPC 1.15, drizzle 0.45, Zod 4, TS 7, Better Auth 1.7 are newer than training data).

## Learned on cards
- 2026-09-30 T-23-2: The floor's mismatch/BLOCKED/outbox-alert path is already generic over `MISMATCH_REASONS` — a new enum value (`station_maintenance`) needed only its `mismatch.*` en/es strings, zero logic changes, and the offline-replay park + lead alert picked it up automatically. Check this before assuming a new mismatch reason needs new code.
- 2026-09-30 T-23-2: `invai-floor/vite.config.ts` and `nginx.conf.template` set `Permissions-Policy: camera=()`, which blocks `getUserMedia` outright — any future camera feature needs `camera=(self)` there first (both files are outside `src/**`/`public/**`, so a narrow-scoped card may need to touch them anyway; flag it, don't skip it).
- 2026-09-30 T-23-2: Demo mode's backend is in-process JS, not real fetch — `context.setOffline()` in Playwright does nothing to it. Test true offline/replay behavior against the real API (`PORT=31xx`), not `?demo=1`.
- 2026-09-29 T-23-2 r2: invai-floor's Vitest setup (`src/test/setup.ts`) does not auto-cleanup between tests (no `@testing-library/react/vitest` import) — any new `*.test.tsx` needs an explicit `afterEach(cleanup)` or later tests see leftover DOM from earlier ones (`getByTestId` throws "multiple elements found"). No existing test in this repo renders `@invai/ui`'s `Dialog`; mocking `@invai/ui`'s Dialog/Button/toast with plain stand-ins is a clean way to unit-test a component's own async ref logic (e.g. a getUserMedia race) without pulling in Radix/jsdom portal behavior nobody else here has set up.
- 2026-09-30 T-P1-5: To unit-test a station's real es.ts strings (not mocked identity keys), call `setupI18n()` + `setLang("es", false)` from `../i18n` in the test (real i18next, synchronous, no network) instead of mocking `react-i18next`; vi.mock("@invai/ui", async (importOriginal) => ({...await importOriginal(), Dialog: ..., BigButton: ...})) keeps `initI18n` real while still stubbing Dialog/BigButton per the Radix-portal lesson above.
- 2026-09-30 T-P1-5: `invai-floor` has no `@testing-library/jest-dom` matchers wired up — `toHaveTextContent` etc. fail typecheck; assert with plain `.textContent`.
- 2026-09-30 T-P1-5: Demo fixture ids are deterministic (`uid(prefix, n)` in `src/api/demo.ts`, n = the item's position among all `item(...)` calls in `makeItems()`, 1-indexed) — useful for building a SimulateScan code (`T:<transferId>`) to reach a specific demo queue row from a script/Playwright run without pairing a real station.
- 2026-10-01 T-P3-2: `mcp__claude-in-chrome` refuses to act when the account has >1 connected browser and demands `AskUserQuestion`, which this role doesn't have — don't fight it. Instead drive the real floor dev server with a scratch Node script using `@playwright/test`'s own `chromium.launch()` (already a devDependency; `page.fill`/`page.keyboard.type`/`page.on("request", ...)` work fine headless), placed at the repo root and deleted before the final commit — not under `e2e/` (QA's) and not committed.
- 2026-10-01 T-P3-2: To force a real 429 from the backend's token-bucket limiter for live verification, `docker exec local-valkey-1 redis-cli -n <db> HSET tb:writes:<companyId> tokens 0 ts <epoch-seconds>` (see `invai-backend/src/lib/ratelimit.ts`) drains the bucket instantly; the next write-bucket call 429s with `retryAfterSec` computed from the refill rate, and tokens refill within a second or two (120 cap / 2 per sec for `writes`), so a short `waitForTimeout` is enough to see the real server verdict replace the busy state.
- 2026-10-01 T-P3-2: Biome's `useExhaustiveDependencies` rejects a closure that is rebuilt every render (e.g. a local `apply(event)` wrapper over `ref.current`) as a `useEffect` dependency ("changes on every re-render"). Fix: keep a `const xRef = useRef(x); xRef.current = x;` in the render body and call `xRef.current(...)` inside the effect — refs are exempt from the exhaustive-deps check and the effect still always calls the latest closure.
- 2026-10-01 T-P3-2 r2: `outbox.ts`'s `flushOutbox` pushes every scan (live-sent or replayed) into `FlushReport.resolved`, by design (outbox.test.ts asserts both). A screen that subscribes to `sync.resolved[clientScanId]` must itself gate on whether its current view is still provisional/queued before re-applying -- a live scan's own just-applied result also shows up there, and re-applying it doubles the sound/render. Gate in the consuming component, don't change what gets published.
- 2026-10-01 T-P3-2 r2: `sync.resolved` is a flat map with no consumer-independent cleanup -- any station whose scans land there but who never calls `takeResolved` (pick, pack) leaks entries for the shift unless something prunes by age. `pruneResolved` in `outbox/sync.ts` (TTL off `entry.sentAt ?? entry.parkedAt`, run on every flush) is the general fix; a component can additionally `clearResolved(id)` on its own unmount/Next for its own abandoned scans.
- 2026-10-01 T-P4-2: A scratch Playwright script's `page.evaluate(async () => (await import("/src/...ts")).thing)` stops sharing the live app's module singletons (zustand stores etc.) once the Vite dev server has served an HMR update to ANY module during the session -- it silently returns a second store instance with default state (session: null) even though the real UI is still logged in, and the bug is invisible until a later call throws "sign in required". Fix: either restart the dev server once after your edits are final and do the whole eval-based flow in one pass, or better, avoid the module graph entirely -- drive the UI through real clicks, and get data via plain `fetch`/curl to the backend with a token from `POST /rpc/floor/login`.
- 2026-10-01 T-P4-2: Draining `tb:writes:<companyId>` to exactly `tokens 0` isn't a safe margin -- refill is continuous (2/sec for `writes`) and a few hundred ms between the `docker exec` and the actual fetch is enough for tokens to climb back above 1, so the "busy" scan goes through for real instead of 429ing. Set `tokens -50` (or similarly negative) for headroom across a couple of calls a few hundred ms apart.
- 2026-10-01 T-P4-2: `/rpc/<proc/path>` (oRPC's RPCHandler, separate from the REST-shaped `.route()` paths the OpenAPIHandler serves) is always POST regardless of the contract's `.route({method})`, and both the request body and the response are wrapped as `{"json": <value>}` -- `curl -X POST .../rpc/floor/login -d '{"json":{"pin":"1155"}}'` is the fast way to get a real floor session/queue data for verification without a browser.
- 2026-10-01 T-P4-2 r2: To screenshot the header's `pending`/`parked` sync pills with a specific count against the real stack, writing fake "pending" `OutboxEntry` rows straight into the `invai-floor` IndexedDB (raw `indexedDB.open`, not Dexie) is fine, but give them a real `sessionToken` (read `kv.session.value.sessionToken` from the same DB) and a schema-valid `ScanInput` command (`station`, `transferCode`, `scannedAt`, UUID `clientScanId`) -- a placeholder/garbage command gets auto-rejected into `status: "parked"` the instant the engine's flush reaches it on reload, even with the write-bucket drained to negative, because oRPC's Zod input validation runs before the rate-limit check. With a valid command, the drained `tb:writes:<companyId>` bucket (see the T-P3-2 entry above) is what keeps them `pending` instead of succeeding outright.
- 2026-10-01 T-P6-3: For a real-backend browser exercise against a non-default API port (e.g. backend-foundation's own `PORT=31xx` test instance), `vite.config.ts` reads `VITE_API_PROXY` (default `http://localhost:3000`) to target `/rpc` and `/events` for `vite dev`'s own proxy -- `VITE_API_PROXY=http://localhost:31xx node_modules/.bin/vite --port 5174` gets a real same-origin SSE/RPC connection with zero CSP friction (dev mode's CSP is always `connect-src 'self'`, unlike `build`/`preview` which bake `VITE_API_URL` into an absolute-origin CSP via `requireApiOrigin`). Simpler than building for prod when you just need to drive the UI once.
- 2026-10-01 T-P6-3: Before assuming an SSE/realtime behavior change needs a new "wiring" file (e.g. an `onUnauthorized` handler), check `useRealtime.ts` first -- it already called `onAuthFailure()` on `onUnauthorized` from an earlier wave, dormant because `connectSse` never actually fired it except on a 401 status. Confirm with `git diff --stat` that the file you assumed you'd need to touch stayed untouched.
- 2026-10-01 T-P6-3: In a scratch Playwright script driving the real floor UI in both languages, detect "landed back on sign-in" by a structural selector (`#station-token` only exists on SetupScreen, `text=/PIN/i` only on LoginScreen's "Enter your PIN" / "Ingresa tu PIN") rather than an English-keyword regex over `body.innerText` -- translated screens (e.g. Spanish "se quitó" for "was removed") silently fail a keyword match and can make a correct, fast transition look like a 30s timeout.
