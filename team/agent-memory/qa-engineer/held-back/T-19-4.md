Held back from backend-foundation until after the T-19-4 report lands, then added to
`invai-backend/src/modules/digest/digest-consent.acceptance.test.ts` and run before review.

1. **Tampered `ref` only (not company/user).** Sign a valid unsubscribe token for
   `{kind: "unsubscribe", companyId, userId, ref: "digest"}`, then forge one for the same
   company/user but `ref: "digest_preview"` (or any other kind's ref) without the secret. Assert:
   rejected (4xx), and — separately — that a *legitimately* signed `click` token for a different
   `ref` than the one the handler expects redirects to that ref's own href, never a caller-supplied
   one (same-origin only, per T-19-4's own AC5).

2. **Expired click token, long-lived unsubscribe token.** `signLink({kind: "click", ...})` should
   expire; `signLink({kind: "unsubscribe", ...})` should not (spec pipeline 13: "unsubscribe tokens
   long-lived"). Freeze time forward past a click token's expiry and assert 4xx; do the same past
   the same duration for an unsubscribe token and assert it still works. Pins the "long-lived"
   requirement as a real behavioral difference, not just a comment.

3. **Suppressed address after a bounce.** `setEmailPreference` alone isn't the only skip path per
   spec pipeline 12 ("suppressed addresses (bounce or complaint)"). Once T-19-4 exposes a
   suppression list write path (its own card doesn't name one explicitly — ask at hand-off), add a
   case: a suppressed address with the preference still `on` still gets `skipped` with reason
   `suppressed`, not `sent`.

4. **`dedupeKey` collision across different subjects.** Call `sendUserEmail` twice with the *same*
   `dedupeKey` but a different `subject`/`text` (simulates a retried digest build that changed
   wording after a partial failure). Assert the second call is a no-op `skipped: duplicate` and
   does NOT send the second, different subject — idempotency must win over "the content changed".

5. **`List-Unsubscribe-Post` header exactly matches RFC 8058.** A byte-exact assertion on the mail
   headers `sendUserEmail` hands to the mailer (`List-Unsubscribe-Post: List-Unsubscribe=One-Click`,
   no extra whitespace/casing), since a near-miss silently breaks one-click unsubscribe in real
   mail clients without failing anything else in the suite.
