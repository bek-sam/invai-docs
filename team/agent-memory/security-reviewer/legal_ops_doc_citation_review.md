When co-reviewing legal/ops docs (T-21-1 legal drafts, T-21-2 incident-response + access-control), the
authors cite `file:line` for almost every claim, so the review is mostly a citation audit, not a code
threat-model: read each cited file at that line and diff the prose against it word for word.

**Where drift actually showed up:** not in the security-relevant claims (encryption, purge jobs, RLS,
PII scrubbing all matched exactly, line-perfect) but in a hand-summarized role/permission bullet list
in `access-control.md` — it said all three floor roles (presser/packer/receiver) share a
`production.qc` baseline, but `invai-contracts/src/roles.ts`'s `RECEIVER` array doesn't include
`production.qc` (only PRESSER and PACKER do). The file's own header even warns "generated by hand, not
derived... reviewers re-check this table" — take that literally and diff every role's array, not just
skim the prose.

**Why:** these docs are explicitly built as evidence for Amazon DPP / Shopify questionnaires
(`security-questionnaire` playbook rule: "MUST NOT answer Yes without verified evidence"), so a wrong
permission claim in the one document whose job is transcribing `roles.ts` defeats its purpose even
though it doesn't touch running code.

**How to apply:** for any future ops/compliance doc citing `roles.ts`, `ROLE_PERMISSIONS`, or any
generated-by-hand table, pull the actual array for every role named and check membership one by one —
don't trust "role X has permission Y, Z" prose against a skim of the roles file. Everything else
(retention days, encryption algorithm, purge job names, SST secret names, deploy.yml permissions) in
these two cards was cited with byte-accurate line numbers — the authors are reliable on single-fact
citations; the risk is in hand-summarized multi-row tables.

**T-21-2 round 2:** the fix matched `roles.ts` exactly; re-verified by pulling PRESSER/PACKER/RECEIVER
arrays directly. Round 2 also added ~15 new file:line citations answering the primary reviewer
(FLOOR_TOKEN_SECRET fallback, PRODUCTION_KEYS boot gate, Stripe live idempotency, alert raise sites,
guard-bash.py rule text) — spot-checked every one directly against code, all accurate (a couple of
raiseAlert call-site line numbers were off by 1-2, immaterial). Gotcha: `guard-bash.py`'s `gh repo
edit` deny rule matches on the substring anywhere in the command, including inside a `grep` pattern
string (e.g. `grep -n "gh repo edit" file.py` gets blocked) — don't be surprised when a read-only grep
for the hook's own rule text triggers the hook.
