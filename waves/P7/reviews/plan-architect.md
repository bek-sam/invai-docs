## R3: T-P7-5: the gateway decides between rounds; the provider only reports each round's end
- **Yes, the gateway can check between rounds.** The runner pulls one step at a time: each `next()` on it runs the previous round's tools, then opens the next request (`BetaToolRunner.mjs:171-230`; `_send` yields the stream at :452-457). The provider is a generator the gateway pulls, so nothing is sent until the gateway pulls again. Today `onUsage` is a synchronous callback (`anthropic.ts:150`), so the gateway can't wait on Redis inside it.
- **Mechanism:** the provider yields an internal event `{ type: "round", usage: cumulative, model: message.model, stopReason }` after `finalMessage()` (on `AssistantStreamEvent` in `src/ai`). The gateway uses it and never passes it on: its loop (`gateway.ts:270`) and the second-pass loop both drop it, so `modules/ai/service.ts` never sees it. Check only when `stopReason` is `tool_use` or `pause_turn`: an `end_turn` round makes no further call and must never turn a finished answer into an error. On a trip: `await gen.return(...)` (the runner's `finally` aborts, and no request goes out), `finishJob` with the usage so far and `stopReason: "spend_cap"` (status `done`, credits charged), then rethrow. Don't let the outer `catch` run `failJob` over it (set `settled` first). The mock provider yields no `round` events, so it is never checked, just as `assertSpend` skips it today.
- **Typed error the web gets today:** `assertSpendAvailable` throws `ORPCError("AI_SPEND_CAP_REACHED")` (`breaker.ts:139`), which also raises the critical alert once a day. `modules/ai/service.ts:1320-1330` catches it and yields the contract event `{ type: "error", code: "spend_cap" }` (contracts `schemas/ai.ts:197-200`). For credits, `assertCredits` → `CREDITS_EXHAUSTED` becomes `code: "credits_exhausted"`. No contract or service change is needed. A gap that belongs to no card here: web `routes/_app/assistant.tsx:140` shows `ev.message` (English server text) and ignores `code`. Add a backlog row for web-engineer.
- **Spend rule (no double count):** keep `recordedCents` per run. After a round, `cum = tokensToCostCents(usageSoFar, model)`, then `recordSpend(cum - recordedCents)` and `recordedCents = cum`. `usageSoFar` already adds the first pass to the regeneration pass. `finishJob` still prices the whole usage as today (that is `ai_jobs.costCents`), but it records only `max(0, costCents - recordedCents)`, including on the disconnect path in `finally`. Never sum per-round `Math.round`ed costs (`models.ts:159`): they drift from today's total. Test: the counter total for the run equals `ai_jobs.costCents`.
- **Credits:** charge once, in `finishJob`, as today. Between rounds, check `assertCredits(tx, companyId, tokensToCredits(usageSoFar) + 1)`, because the balance hasn't moved yet. That is the check-after rule for AC4.
- Accepted risk to state in the report: parallel questions can overshoot a cap by at most one round each.
