## Acceptance criteria
1. Every deploy-time failure listed in B-57 is fixed: imaging reachable by an internal URL (service discovery), worker env (`BETTER_AUTH_URL`, `WEB_ORIGIN`, `FLOOR_ORIGIN`), stage URLs from one registrable domain (`[[OWNER: domain]]` read from an SST variable, never hard-coded), imaging S3 config, ACM + HTTPS listener (HTTP redirects), `IMAGING_SHARED_SECRET` to api/worker/imaging, ECS `stopTimeout` ≥ 35 s, health checks on `/readyz`.
2. Valkey: cluster mode off, `maxmemory-policy noeviction` (B-02). RDS: size by stage, backups 14 days (prod), deletion protection and final snapshot in production, `rds.force_ssl`, Pool `ssl` (B-74). S3: lifecycle rules match real key prefixes, CORS limited to the stage origins, versioning (B-73). KMS key for field encryption (consumed by T-24-2). WAF on the ALB and CloudFront in production, S3 gateway endpoint, ARM64 tasks (B-107).
3. Every secret the backend's production guard requires (`src/env.ts` `PRODUCTION_KEYS`) is an `sst.Secret` wired to the right services (B-77); `ALLOW_MOCKS` only on a named demo stage.
4. The migrate one-off task runs `node dist/db/bootstrap-cli.js`, then `migrate-cli.js`, then `reference-seed-cli.js` (the wave's agreed interfaces), as the right DB users.
5. Verification without AWS: `pnpm typecheck && pnpm lint` in invai-infra; if SST can type-check or diff without credentials, do it; otherwise say so. No `sst deploy`, no `aws`, no secret set (the guard blocks them anyway).
6. A table in the report: every owner input (account, region, domain, secrets, SES) with the SST variable or secret name that consumes it; the docs-writer turns it into the OI checklist in T-24-4.
