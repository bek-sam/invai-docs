## Decisions
- **`vite preview`, not `vite dev`, for the manual/browser verification server.** `vite.config.ts`
  (architect/platform-owned, not mine) hardcodes the dev-mode CSP's `connect-src` to
  `http://localhost:3000` regardless of `VITE_API_URL` (only `build`/`preview` honor it, per the
  file's own comment: "never served: only `devCsp` above governs plain `vite`/`pnpm dev`"). Against
  my API on 3151, `pnpm dev` blocks every API call with a CSP violation. I built with
  `VITE_API_URL=http://localhost:3151 pnpm build` and served with `vite preview --port 5199
  --strictPort` (also `VITE_API_URL` set, since `prodCsp` reads it at request time), which is still
  "the web dev server on a free port" the card asks for, just the production-CSP-correct way to
  point it at a non-default API port. Not a code change; noted for whichever wave later gives every
  agent its own port a way to do this without rebuilding.
- **Vote cards fetch full `MarketRecommendation` records via `market.recommendations.list({ids})`**,
  not just the stream's `RecommendationRef`, because the fixed per-rule action text needs `params`
  (design name, channels, blank, floor price, etc.), which only the full record carries. One extra
  call per turn that shows recommendations; capped at the ids in that turn (≤3).
- **Niche chip renders as one `Badge` with combined text** ("Niche: Teacher" / "Niches: Teacher,
  Retirement"), not per-niche chips. The spec's copy table and QA's e2e both check this as one
  literal string; per-niche visual chips (my first draft) don't produce that exact text (no
  separator between adjacent inline elements), so I matched the spec's literal wording instead of
  inventing a chips-in-a-row look.
- **Removed the Send button's `disabled={!input.trim()}`**: safe because `ask()` already no-ops
  on an empty/whitespace message; needed because QA's `askStarter` helper polls this exact button
  as the "streaming finished" signal, and it never types into the textarea (uses starter buttons).

## Known gaps and follow-ups
- **QA's `e2e/market.spec.ts` test 1 ("no failed requests") never passes as written, for a
  pre-existing reason unrelated to T-18-5.** Every `ai.assistant.ask()` call — including a wave-17,
  non-market question ("Are my ads paying off?") that I reproduced the same way — logs one
  `net::ERR_ABORTED` on `POST /rpc/ai/assistant/ask` even though the request returns 200 and the
  full stream is received correctly. Root-caused to how `@orpc/client`'s RPCLink event-iterator
  handles the terminal SSE frame for a streamed procedure (it appears to cancel the fetch reader
  after its own last event rather than let the browser close the stream), which Chrome's network
  layer reports as an aborted request regardless of the 200 and complete body. This is in
  `@orpc/client` / `ai/service.ts`'s streaming transport, neither of which is in my owned paths,
  and it predates wave 18. **Routed to:** ai-engineer / architect (owns the `ai.assistant.ask`
  streaming implementation and its oRPC usage) to confirm and fix or accept; qa-engineer, since
  `watchPage`'s zero-failed-requests assertion will keep failing on *every* assistant answer until
  it does, not just market questions.
- **QA's `e2e/market.spec.ts` "vote survives reload" and "Spanish" tests can collide with sidebar
  history.** `askStarter`'s `page.getByRole('button', {name: text})` isn't `exact`, so once two
  conversations share the same starter text (which `firstAnswerWithVotes` deliberately creates by
  looping through all 3 starters hunting for one with recommendations — only the holiday/
  seasonality starter yields any on this seed), a later call to the same starter text matches both
  the sidebar entry and the (if present) starter button, and Playwright throws "strict mode
  violation" instead of clicking either reliably. Reproduced deterministically. **Routed to:**
  qa-engineer — either scope `askStarter`'s locator to the empty-state container, use `exact: true`
  plus a `main`-scoped locator, or start each test from a state where the seed already yields votes
  on the first starter (backlog item, already flagged in `wave.md`: "Halloween on the seed is the
  expected source" for votes; the other two starters currently yield none for Desert Bloom).
- **QA's "Spanish" test sets `invai.lang=es` before `loginAs`, but the shared `loginAs` helper
  (`e2e/helpers/ui.ts`) hardcodes `getByLabel("Email")`.** The login page's field is "Correo" once
  the locale is Spanish before login, so the test times out at `loginAs`, never reaching my code.
  Reproduced directly (`getByLabel("Correo")` finds it, `getByLabel("Email")` doesn't, once
  `invai.lang=es` is set before navigating to `/login`). **Routed to:** qa-engineer (owns
  `e2e/helpers/ui.ts`) — `loginAs` needs to accept either label, or the Spanish test needs to set
  the locale after login instead of before. I verified AC15 (Spanish chips, badge, no English)
  directly instead: screenshot `t18-5-assistant-es-390.png`.
- **QA's "niche chip" test assumes the catalog's first-listed design starts with 0 niches** (its
  unconditional `pick("Teach","Teachers"); pick("Retire","Retirement")` expects both to succeed
  regardless of what the design already has, then expects the saved result to be exactly
  `["teacher","retirement"]`). On Desert Bloom's seed, the first-listed design ("Lake Powell
  Weekend") already carries one mapped niche (`vacation-group`) after the nightly jobs run, so my
  correctly-implemented "refuse (disable) a third once 2 are selected" (matching the spec's "at
  most 2" and the *other* part of the same test, which explicitly expects a real 3rd pick to be
  refused) blocks the second explicit pick too, since the pre-existing niche already occupies one
  of the two slots. I verified the actual behavior directly against a design that starts
  unclassified (`Saguaro Sunset`): 0 -> pick 2 -> a 3rd option is `aria-disabled`/unclickable ->
  save -> exactly the 2 picked niches, then restored the design's state. **Routed to:**
  qa-engineer — either the test should clear the target design's niches via the API before opening
  the picker (as it already does to restore the original afterward), or pick a design known to
  start unclassified.
- Given the above four items are either pre-existing (the abort) or in QA's test/fixture code
  (not mine to edit), I did not weaken, skip, or edit `e2e/market.spec.ts`; I verified the
  underlying behavior with a throwaway copy (deleted before finishing) and directly with Playwright
  scripts against my own servers.
- Recommend product-designer promote the local `ConfidenceBadge` into `@invai/ui` before wave 19's
