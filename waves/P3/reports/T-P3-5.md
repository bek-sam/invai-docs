# Report: T-P3-5 Market tests stop leaking rows into the global series cache (B-221)
Author: backend-engineer (market) on Opus 5.5

## Built
- `src/modules/market/service.test.ts`: 4 describe blocks whose `beforeAll` writes the global
  `market_series_cache` (via `runAll()` → `market.refreshDemand`) now also clear it in their
  `afterAll`, matching the pattern already used by the blocks that were self-protecting:
  - "happy path on a fixture shop (AC1, AC3)" (was: `afterAll(() => vi.useRealTimers())` only)
  - "price position, simulate_price, R2/R3 (AC4–AC6, AC19)" (same gap)
  - "mock visibility rule (AC29, AC22)" (2nd test writes via `runAll` inside a try/finally that
    reset env/timers but never cleared the cache)
  - "recommendations: tenancy, votes, shown, feedback, digest" (same gap)
- No product code changed: `clearCache()` already existed as a private helper in this file
  (`const clearCache = () => withSystem((tx) => tx.delete(marketSeriesCache));`), so no
  `clearCache()`-style helper was missing.
- `engine.test.ts` never touches `marketSeriesCache` (pure-function tests only) — nothing to fix there.

## Root cause (for the record)
Actual file execution order under `fileParallelism:false` is **not** alphabetical:
`market.acceptance.test.ts` → `service.test.ts` → `market-outage.acceptance.test.ts` →
`market-prod-mode.acceptance.test.ts` (confirmed from log order across 5 runs; `market-scale.acceptance.test.ts`
is skipped by default). Within `service.test.ts`, "happy path" and "mock visibility" already
cleared the cache *before* writing, so they were safe from upstream pollution, but none of the
four blocks above cleared *after* writing. That let frozen-date rows from one block (e.g. NOW =
2026-09-01) leak into the next block's reads (e.g. "price position" at NOW = 2026-09-15, which
never cleared before starting either), corrupting trend/seasonality signal computations that scan
all cached periods for a query. The file-level `afterAll` (pre-existing, unchanged) still clears
everything once at the very end, so this never leaked *out* of the file — the damage was
intra-file, between describe blocks.
