## Blocking findings
1. `ops/incident-response.md:102` — States "No Etsy-specific breach-notice clause is recorded yet in our compliance docs" and invents a default. Our docs already record it: `research/10-marketplace-engineering-rules.md:75` (R14) and `:135`, "within 24 h to `dpo@etsy.com` and to the seller." AC1 asks for the Etsy notice path. Failure: during a PII incident involving Etsy orders, the owner has no recipient address and follows a "treat like Shopify" default. Fix: give the real path (24 h, dpo@etsy.com plus the seller, cite research 10) and keep the "compliance-officer re-verifies the live terms" note.
2. `ops/incident-response.md:123-125` (§6.1 step 3) — Says rotating `BETTER_AUTH_SECRET` "signs every web session out." It also changes `FLOOR_TOKEN_SECRET`, because that falls back to it (`invai-backend/src/env.ts:227`) and is not an SST secret (`sst.config.ts:75-80`). `hashPin` (`floor-auth.ts:162`) and floor session signing (`:211`) use it. Failure: after a leak the owner rotates BetterAuthSecret as written. Every stored PIN hash in every tenant stops matching, so no presser, packer or receiver can sign in on the floor: a platform-wide SEV2 caused by the containment step. Fix: warn about this in the step (PINs must be reset, or set `FLOOR_TOKEN_SECRET` separately first), and add `FLOOR_TOKEN_SECRET` rotation as its own step.
3. `ops/incident-response.md:128-130` (§6.1 step 4), `:176-178` (§6.4 step 3), `ops/access-control.md:99` ("empty string default → mock provider") — These describe mock fallbacks and a stubbed Stripe that production no longer has. (a) Production refuses to boot with a provider key missing unless `ALLOW_MOCKS=true` (`env.ts:173-199`). Until rotation the app runs on the *leaked* key, not a mock, and blanking the key makes the API fail to start. (b) Stripe is live when `STRIPE_SECRET_KEY` is set: Checkout plus a webhook with Stripe event-id idempotency (`billing/service.ts:28-32`, `billing/stripe-events.ts:30`, B-53 done in wave 2). Research 12 G12 is out of date. Failure: an IC reads §6.4, rules out a real billing charge ("can only be a code bug, not a real charge") and doesn't contain it at Stripe while charges repeat. Fix: rewrite both steps to match `env.ts` and the billing module.
4. `ops/access-control.md:100` (§5 "Not yet SST-managed") — The inventory omits production secrets that are also not in SST: `IMAGING_SHARED_SECRET` (a `PRODUCTION_KEYS` entry, `env.ts:54,182`), `FLOOR_TOKEN_SECRET` (`env.ts:61`), and `SMTP_URL`/`MAIL_FROM` (`env.ts:112-113`, which carries mail credentials). §6.1 has no containment step for `IMAGING_SHARED_SECRET` or `FLOOR_TOKEN_SECRET`. AC2 asks for secret storage. Failure: this table is answered on the Shopify/Amazon questionnaire as the complete secret list. A leaked imaging secret (which lets a caller use the internal render service) has no step and no owner. Fix: add the missing rows and cite B-77, which already tracks most of them. Two §6.1 steps are enough.
5. `ops/incident-response.md:47-57` (§3 detection table) — (a) `qc_fail_spike` is listed as a working detection source for wrong-art tenant leaks, but nothing in `invai-backend/src` raises it (grep returns 0 hits). (b) The "Severity in schema" column is not in the schema: `alerts.ts` has no per-kind severity, and `sync_broken` is raised as `critical` by `today/service.ts:348`. (c) Every one of these alerts is a row in the *affected shop's* `alerts` table (`raiseAlert(tx, companyId, ...)`, e.g. `sweeps.ts:80-81`, `breaker.ts:107-108`). The IC (an InvAI role) can't see them, but the text says "a human must be looking at Today." Failure: the incident plan counts on a qc spike alert that never fires, and on InvAI staff seeing alerts that only reach shop users. That overstates detection in the evidence we show Amazon. Fix: mark `qc_fail_spike` "defined, not raised yet", drop or correct the severity column, and say plainly that these alerts reach the shop, not InvAI, until B-75 (paging) lands.
6. `ops/access-control.md:39` and `:99` — Claims that `.claude/hooks/guard-bash.py` blocks agents from branch-protection API calls and from `sst secret set`. Probed: both return rc=0 (not blocked). The hook's deny list (lines 65-74) covers `sst deploy/remove`, `gh secret`, `gh repo edit` and `gh api ... secrets|/keys|DELETE`, but not `sst secret` or a `PUT .../protection`. Failure: the policy tells Amazon/Shopify that a technical control stops agents from changing production secrets. With AWS credentials present, an agent following §6.1 could run `sst secret set` and nothing would stop it. Fix: state these as owner-only by policy (not enforced), and ask the tech lead for a hook card (the hook is outside platform-sre's paths). Don't claim enforcement until it exists.
