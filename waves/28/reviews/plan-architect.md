# Wave 28 plan review: architect (design co-review)
Reviewer: architect (opus). Inputs: wave.md, T-28-1..5, code read-only. Verdict: **changes-required** (6 blocking, all card-text edits; no redesign)

## Blocking
1. **Vendor role can never match.** Vendor orgs only carry role `vendor` (`contracts/src/roles.ts:4`, `roleFits` `backend/src/api/context.ts:86`), so "owner or admin, vendor portal included" (T-28-2 AC8, T-28-4 AC6) is impossible. Edit: pick the set explicitly as `MFA_REQUIRED_ROLES` in ADR 0025. Recommend owner+admin only: delete "the vendor portal included" from T-28-2 AC8, replace T-28-4 AC6 with "vendor users see no banner; nothing changes in invai-floor", and record "vendor excluded (no buyer PII in the portal)" in 0025 for the security reviewer. If security wants vendors covered, add `vendor` to the set and keep AC6.
2. **Active org vs any org.** T-28-1 (`Me.mfa.required` = active org role) and T-28-2 AC8 say active org; AC11 and wave.md say any org. With active org, an owner of A who is office in B escapes enforcement through `me.switchOrg` (which is allow-listed), yet AC11 refuses their disable. The banner would also flicker with the org switcher. Edit everywhere (T-28-1 Me doc, T-28-2 AC8/AC10/AC11, T-28-4 AC5): "required = the user holds an **active** owner/admin membership in any **non-sample** org (`context.memberships`)".
3. **Sample workspace makes everyone an owner.** `startDemo` inserts `role: "owner"` (`modules/tenancy/demo.ts:81`), so an office or designer user who opens the sample shop would become MFA-required (under either rule). Edit T-28-2 AC8: "memberships in `companies.demo = true` orgs don't count". Note that `Membership` (`context.ts:22`) has no demo flag yet; T-28-2 adds it (owned path).
4. **Lockout leaks which accounts exist.** A per-user counter means only real emails ever answer 423, which contradicts AC4. Edit T-28-2 AC1/AC4/AC5: key the counter on the normalized email (lowercase, trimmed) stored as an HMAC (never the address) in a global table such as `sign_in_failures(email_hmac pk, failures, locked_until, notified_at)`. Count atomically with `INSERT … ON CONFLICT DO UPDATE SET failures = failures + 1 RETURNING`. Unknown emails lock the same way. The email is sent only when a user exists and `failures` crosses the threshold exactly (that gives AC3's one-email rule). Password reset deletes the row (`onPasswordReset` has the email). Feasibility checked: Better Auth 1.7.5 runs before-hooks ahead of the endpoint and runs after-hooks with the endpoint's APIError in `ctx.context.returned` (`dist/api/dispatch.mjs:210-245`), so the before-hook refuses before any session exists. better-call 1.4 has `LOCKED: 423` (`error.mjs:77`): `new APIError("LOCKED", { code: "ACCOUNT_LOCKED", message, retryAfterSec })`.
5. **Two-step disable refusal has no agreed code, and the codes have no home.** T-28-2 AC11 says "for example `MFA_REQUIRED`". Reusing the oRPC code for an opposite meaning ("turn it on") makes the web route a user who *has* two-step to the setup page. Edit the wave.md interfaces and T-28-1: add to the contract (pure constants plus one schema, additive) `AUTH_ERROR_CODES = ["ACCOUNT_LOCKED", "PASSWORD_REUSED", "MFA_DISABLE_NOT_ALLOWED"] as const` and `AccountLockedBody = z.object({ code: z.literal("ACCOUNT_LOCKED"), message: z.string(), retryAfterSec: z.number().int() })` in `src/schemas/tenancy.ts`. Statuses: 423 / 400 / 403; thrown from `auth.ts` before-hooks on `/sign-in/email`, `/change-password` + `/reset-password`, and `/two-factor/disable`. Document them in the README auth section too. Answer to your question: in the contract as constants, not README only. Both repos then share the literal, and a typo fails typecheck (`auth-errors.ts` switches on strings today).
6. **Ownership gaps.**
   - T-28-1: `CONTRACT_VERSION` lives in `src/compat.ts:8` and is pinned in `src/photos.test.ts:432`. Add both to the owned paths, and relax the photos pin to "at least 0.12.0" (only the newest wave pins).
   - T-28-4: the toast suppression list `DIALOG_EXPLAINED_CODES` is in `invai-web/src/main.tsx:20`, which is not owned. Add `src/main.tsx` (MFA_REQUIRED must not toast). Name the shell file exactly: `src/routes/_app.tsx`.

## Optional
7. MFA check placement (T-28-2): in `guard` (`api/orpc.ts:127-132`), after the permission check and before `EMAIL_NOT_VERIFIED`, only when `context.sessionKind === "user"` and mode ≠ public/station, with `MFA_EXEMPT_PROCEDURES = {me.get, me.switchOrg}`. Note: SSE `/events` and `/l` links sit outside oRPC; accept that in 0025.
8. Grace without a backfill: `users.mfa_grace_starts_at timestamptz NOT NULL DEFAULT now()`. In PG 17 this is metadata-only, and existing rows get the migration time, which is exactly "the later of creation and migration". Deadline = start + `MFA_GRACE_DAYS`. Consider resetting it when a user is promoted to owner/admin; otherwise a promoted admin is blocked at once.
9. T-28-4 AC4 dead end: turning on two-step needs a verified email (`auth.ts:274`). A past-deadline, unverified owner sees "sign-out only". The setup page should also offer "resend verification email". Put it outside `_app` (like `verify-email.tsx`) so the `_app` redirect can't loop.
10. Password history: use `databaseHooks.account.create/update.after` to append the hash, which covers sign-up, invite, reset, change and seed. Refuse in the before-hook with `ctx.context.password.verify` (reset: find the user via `reset-password:<token>`, `routes/password.mjs:125`). Ten scrypt checks take about 0.5–1 s, inside the existing 10/15 min limit.
11. `decisions/README.md` gets a row from both T-28-2 and T-28-3. Stage by hunk; the tech lead commits them in order.

## T-28-3 / T-28-5 (blocking items 12–13 are AC fixes)
12. **Blocking:** "refunded" is not an order status (`contracts/src/states.ts:73`). Final states are shipped, delivered and cancelled. Edit AC2.
13. **Blocking:** the batch loop needs a "still holds drop data" predicate (like `holdsPii`, `privacy/service.ts:749`). Otherwise `for(;;) … limit 500` re-selects swept orders forever, and AC4's "second run changes nothing" never ends. Edit AC4 to require it. Drop columns that are NOT NULL get a fixed placeholder, and the card says which.
14. Use the module's month cutoff (`buyerPiiCutoff`, `setUTCMonth - 18`, on `orders.placedAt`) instead of a second 548-day rule.
15. T-28-5 is sound: the only two enqueuers are `sync.ts:505` (jobId) and `jobs.ts:66` (null). But `handleWebhook` (`sync.ts:905`) still imports when auto-import is off, so the wave goal "gets no more imported orders" is false for webhook channels. Narrow the goal to "no more polled imports", or ask the PM whether webhooks should skip new orders (keep cancels).
