## Acceptance criteria and their tests

1. **Per-tenant API rate limits, Valkey token bucket.** `lib/ratelimit.ts`'s `takeToken`/`checkRateLimit`: one Redis `EVAL` (read-refill-decide-write) per bucket key `tb:{bucket}:{companyId}`, four buckets (`auth`, `reads`, `writes`, `ai`) with independent capacity/refill. `api/orpc.ts`'s `rateLimit` middleware (in the `pub` chain, after `guard`) classifies each procedure via `bucketFor`: `ai.*` path → `ai`; `auth: "station"` meta (floor PIN login, the PIN-screen staff list) → `auth`; GET → `reads`; else → `writes`. Skipped when `context.companyId` is null (public procedures — nothing to key on). `RATE_LIMITED`'s `retryAfterSec` is set as both the error `data` and an HTTP `Retry-After` header via `context.resHeaders` (new `ResponseHeadersPlugin` in `api/app.ts`, wired into `Context` in `api/context.ts`). Tests: `lib/ratelimit.test.ts` (N+1 inside the window → denied with `retryAfterSec`; after waiting, the next request is admitted; buckets and companies stay independent), `api/ratelimit.test.ts` (real `call()` through the middleware gets `RATE_LIMITED` + header; a real HTTP request via `app.request()` gets a 429 with a `retry-after` header).
2. **Better Auth rate limiting moved to Valkey.** `auth.ts`'s `rateLimit.customStorage: { consume: betterAuthConsume }` (not `secondaryStorage` — that option also engages session/verification caching paths in Better Auth's internal adapter, which is out of scope and risky to change here; `customStorage` only replaces the rate-limit counter). `betterAuthConsume` (`lib/ratelimit.ts`) is a fixed-window Redis `EVAL` matching `BetterAuthRateLimitStorage["consume"]`'s exact shape. Test: two direct calls alternating as "process A"/"process B" against the same key share one Redis-backed count and trip `max` together (would each see their own 1/2/3 and never trip it under the old per-process `Map`).
3. **Fail-open on Redis trouble.** Every new check (`takeToken`, `betterAuthConsume`, `acquireSlot`) wraps its Redis call in the same `withTimeout` (500ms) + try/catch convention already in this file for PIN lockouts, and returns "allowed" on error/timeout with a `log.warn`. Tests mock `redis.eval` to hang forever or reject, and assert the request is allowed, not 500'd.
4. **Per-tenant job fairness.** `lib/fairness.ts`'s `withFairness(companyIdOf, process)` wraps the worker's processor (`worker/index.ts`: `withFairness(companyIdFromData, processJob)`). A per-`{queue, companyId}` Redis set (`sem:{queue}:{companyId}`) caps concurrent jobs via one `EVAL` (SISMEMBER/SCARD/SADD, atomic); over the cap, the job re-delays itself (`job.moveToDelayed` + `throw new DelayedError()`) rather than running or failing — confirmed against `node_modules`: BullMQ's `handleFailed` treats `DelayedError` as "move to active for the next job," not a failed attempt. The cap (`capForQueue`) scales off each queue's real `QUEUE_CONCURRENCY` (`concurrency - 1`, minimum 1) instead of a flat number — **see "What I fixed" below**, the flat default the fairness code first shipped with actively hurt an uncontested tenant. Test (`fairness.test.ts`, real BullMQ `Queue`/`Worker` against this card's Redis DB): tenant A enqueues 200 jobs, tenant B enqueues 5; B's jobs all complete within 8s (a concrete bound, derived from A alone needing ~4s for its own admitted work at cap) while most of A's backlog is still unfinished.
5. **Priority for interactive vs bulk jobs.** `BULK_PRIORITY = 10` (`fairness.ts`). BullMQ dequeues jobs with no explicit priority before any prioritized job regardless of enqueue order (confirmed in `node_modules/bullmq`'s own doc comment), so giving only bulk kinds a priority is sufficient — interactive jobs need no change. Wired: `channels/sync.ts`'s `importCsvJob` (`channels.importCsv`) already had `priority: 10` from wave 3; this card adds `modules/ai/jobs.ts`'s `generateListingDrafts` (batch AI) and `lib/queues.ts`'s `reports` queue default (every job there is a sweep, never interactive) — both flagged out-of-owned-path, commit `1d077e2`. Test (`fairness.test.ts`): 50 bulk-priority jobs cold in the queue, then one no-priority job; the no-priority job is picked up within the first 25 of the 50-job backlog (in practice, first).
6. **Channel poll jitter.** `modules/channels/jobs.ts`'s `pollJitterMs(connectionId)`: FNV-1a hash of the connection id mod `POLL_EVERY_MS`, passed as `enqueue(..., { delay: pollJitterMs(c.id) })`. Test (`jobs.test.ts`, new file): 100 random connection ids give more than 50 distinct offsets, all in `[0, POLL_EVERY_MS)`; the same id gives the same delay every call; two fixed ids give different delays.
7. **Load-test evidence**, `scripts/t12-3-fairness-loadtest.ts` (run: `REDIS_URL=redis://localhost:6379/14 pnpm tsx scripts/t12-3-fairness-loadtest.ts`). Uses the real queue name `"sync"` (concurrency 10) so `capForQueue` resolves the same cap production would. Tenant A: a 3,000-row CSV import, chunked 100 rows/job like the real `channels.importCsv` (30 jobs, `priority: 10` in the "after" run). Tenant B: 5 single order syncs (matches AC4's own ratio), no priority. 150ms of fake work per job (a realistic DB-chunk write).

   | | tenant B latency (p50/p95/max) | tenant B fully drained |
   |---|---|---|
   | **Before** (no semaphore, no priority — plain FIFO) | 611ms | 611ms |
   | **After** (T-12-3 semaphore + bulk priority) | 309ms | 309ms |

   B's floor after the fix (~309ms = one round of already-active, unpreemptable A work + B's own 150ms) is the honest limit of this design: the semaphore stops a tenant from *holding* more than `concurrency - 1` slots, and priority stops a tenant's *pending* backlog from blocking B's dequeue order, but neither can preempt a job already running. That matches the card's own framing ("must not starve," not "must run instantly").

## What I fixed (a real bug the load test caught)

The rate-limit and fairness mechanism was mostly built by a research fork I'd launched to answer a narrower question (how to categorize procedures into rate-limit buckets) — it went further than asked and implemented working code for most of this card (correctly avoiding the `secondaryStorage` trap in item 2, and independently landing on nearly the same token-bucket/semaphore designs I'd have written). It hit its session's rate limit mid-task and stopped after writing `fairness.test.ts`, before writing `jobs.test.ts` or the load-test script.

Its first cut of `fairness.ts` used a **flat `TENANT_CONCURRENCY_CAP = 2` for every queue**. My first load-test run showed the "after" scenario *slower* than "before" (p95 1563ms vs 88ms) — the cap applied to tenant B too, throttling B's own jobs to 2-concurrent regardless of tenant A's presence, on a queue whose real concurrency is 10. I changed the cap to scale off each queue's `QUEUE_CONCURRENCY` (`capForQueue`, `concurrency - 1`, minimum 1) so a lone tenant is never throttled below "everyone else gets at least one slot," reran the load test, and confirmed the direction flips correctly (see the table above). All tests were rerun after the fix.

## Decisions (and why)

- **`customStorage`, not `secondaryStorage`, for Better Auth's rate limiter.** `secondaryStorage` also changes how Better Auth caches sessions and verification tokens internally (confirmed by reading `better-auth`'s `internal-adapter.mjs`) — setting it would risk session rows silently stopping being the source of truth, which nothing else in this codebase expects. `customStorage`'s `consume(key, rule)` shape does exactly the one thing item 2 asks for.
- **Cap scales per queue, not a card-literal "2".** wave.md's semaphore example ("at most 2 render jobs") is illustrative — taken literally as a flat default it actively hurts a queue with real concurrency 10 (`sync`), as the load test showed. `capForQueue` keeps the spirit (always leave a tenant able to be starved *by* the cap, never *of* the cap) without the regression.
- **Priority alone would starve nothing already active; the semaphore covers that gap.** Priority only reorders BullMQ's *pending* wait list. A tenant that already has jobs active when another tenant's job arrives isn't affected by priority — the semaphore's `capForQueue` guarantee (never more than `concurrency - 1` slots to one tenant) is what bounds that case.
