# T-12-2 Health, timeouts and graceful shutdown

Backlog B-16 (P-G6-8). **Runs in parallel with T-12-3 and T-12-4, after T-12-1 lands** (see `wave.md`, "Ownership split"). Owned files: `src/api/server.ts`, `src/db/migrate.ts`, a new role-timeout migration. Coordinate on: `src/api/app.ts` (adds `/livez`/`/readyz` next to `/health`, additive) and `src/worker/index.ts` (owns only the `shutdown()` function — T-12-3 owns the `Worker` processor callback in the same file, a different region).

## Acceptance criteria (each item has its own test)

1. **`/livez` vs `/health` vs `/readyz`.**
   - `/livez` returns 200 whenever the process is up, with no DB/Redis/imaging/S3 calls (test: with the DB pool forcibly down, `/livez` still returns 200 fast, under e.g. 50ms).
   - `/readyz` returns 503 when DB or Redis is down, 200 otherwise (same dependency checks `/health` already does).
   - `/health` is unchanged (kept for the dashboard, per-integration mock/live detail).
   - Test: a DB outage that would have failed `/health` today must not fail `/livez`.
2. **DB role-level timeouts.** A migration sets, on the app role: `statement_timeout = '15s'`, `idle_in_transaction_session_timeout = '30s'`, `lock_timeout = '5s'` (research doc §1, role-level so they survive any pooler). Test: a query that runs longer than `statement_timeout` inside a test transaction is cancelled by Postgres, not by the app; assert the error surfaces as a typed 5xx, not a hang. A separate, longer timeout for the system/reports role (e.g. 5 min) is documented and tested for the purge/export jobs that need it.
3. **Graceful SIGTERM — API.** On SIGTERM: stop accepting new connections, let in-flight requests finish (bounded by N seconds), close SSE streams with a retry hint the client can act on, then exit. Test: start a slow in-flight request, send SIGTERM, assert the request still completes and the process exits only after it does (or after the N-second cap, whichever first) — not immediately.
4. **Graceful SIGTERM — worker.** Confirm/extend the existing `shutdown()` in `worker/index.ts`: `worker.close()` must wait for active jobs up to an explicit N-second cap before forcing exit (today it awaits unconditionally with no cap, which can hang past the deploy's real timeout budget). Test: a job that runs longer than N seconds is still running (not killed) at N-1s and the process force-exits at N+epsilon.
5. **Migrate advisory lock** (T-1-5 review: concurrent migrates on a fresh DB race on `CREATE EXTENSION`). `runMigrations` takes a Postgres advisory lock (`pg_advisory_lock`, a fixed known key) before running migrations + `ensureReferenceData`, and releases it after, including on error. Test: run `runMigrations` twice concurrently against the same fresh database and assert no error and no duplicate/partial extension creation — the second call simply waits then no-ops cleanly.
