# T-12-3 Rate limits and queue fairness

Backlog B-20 (P-G12, P-G13). **Runs in parallel with T-12-2 and T-12-4, after T-12-1 lands** (see `wave.md`, "Ownership split" and "Fairness"). Owned files: `src/lib/ratelimit.ts`, new `src/lib/fairness.ts`, `src/auth.ts`. Coordinate on: the rate-limit middleware in `src/api/orpc.ts`/`context.ts`; `src/worker/index.ts` (owns only the `Worker` processor callback — T-12-2 owns `shutdown()`); `src/modules/channels/jobs.ts` (poll jitter, land after T-12-1's edit there, not before).

**BullMQ Pro "groups" is not installed** (only open-source `bullmq@6.3.8` is in the lockfile — see `wave.md`). Build the free alternative: a per-`{queue, companyId}` Valkey semaphore plus lower `priority` for bulk job kinds. Don't add `bullmq-pro` as a dependency.

## Acceptance criteria (each item has its own test)

1. **Per-tenant API rate limits, Valkey token bucket.** Separate buckets for `auth`, `reads`, `writes` and `ai`, keyed by `company_id` (not by IP). Exceeding a bucket returns the existing `RATE_LIMITED` error (`COMMON_ERRORS`, already has `retryAfterSec`) with a matching HTTP `Retry-After` header. Test per bucket: N+1 requests inside the window get `RATE_LIMITED` with a `retryAfterSec` that, after waiting, actually admits the next request.
2. **Better Auth rate limiting moves to Valkey** (T-2-3 follow-up: today it's in-memory per process, so two API tasks each allow the full quota). Test: simulate two "processes" (two separate rate-limit-checking calls sharing one Redis instance) and assert the combined count — not each process's own count — trips the limit.
3. **Redis/Valkey failure behavior is explicit and tested**, matching the existing `lib/ratelimit.ts` fail-open convention: a rate-limit check that times out against Valkey allows the request and logs a warning (already the pattern for PIN lockouts) — write a test that forces the Redis call to time out and asserts the request is allowed, not 500'd.
4. **Per-tenant job fairness**, the semaphore described in `wave.md`: at most K concurrent jobs per `{queue, companyId}}`; a job over the cap re-delays itself (`moveToDelayed` + `DelayedError`) rather than occupying a worker slot or failing. Test with 2 tenants: tenant A enqueues 200 `render` jobs, tenant B enqueues 5; assert tenant B's jobs complete within a bounded time regardless of A's backlog (not "eventually" — assert a concrete wall-clock bound in the test).
5. **Priority for interactive vs bulk jobs.** Bulk kinds (`csv_import`, batch AI, `reports`) get a lower BullMQ `priority` than interactive ones (label buy, single render). Test: with the queue full of bulk jobs, an interactive job enqueued after them is still picked up before most of the bulk backlog.
6. **Channel poll jitter.** `pollChannelsJob`'s fan-out no longer enqueues every connection at the same instant; each gets a stable delay of `hash(connectionId) % POLL_EVERY_MS`. Test: enqueue 100 connections' worth of poll jobs and assert their scheduled times are spread, not identical, and that the same `connectionId` always gets the same delay (stable, not random per run).
7. **Load-test evidence with 2 tenants** (required artifact, not just a unit test): a short script or `k6`/`autocannon` run showing tenant B's p95 latency under tenant A's bulk load, before and after the semaphore, attached to the task report.

## Explicitly out of scope (flagged in `wave.md`)
The per-tenant DB-time dashboard and a `tier` column on `companies` (research §2.3/2.5) are "SHOULD (next)", not this wave. Sharding hot queues by `hash(companyId) % K` is a fallback only if the load test in item 7 shows the semaphore isn't enough — don't build it pre-emptively.
