## `packOrder` contract design, and the order-level packed state
No `production.packOrder` procedure exists today — confirmed nothing in `modules/production/{router,floor,sheets}.ts` calls anything like it, and `PackStation.tsx`'s current `finish()` only releases the bin and fetches a label URL; it never asks the server whether the order is actually complete. This card is a real gap close, not polish.

The harder question is the order-level state. `ORDER_STATUSES` in `invai-contracts/src/states.ts` documents itself as "derived from its items... never stored as truth," but `orders.status` **is** a stored column (`db/schema/orders.ts`), rewritten by `recomputeOrderStatus` (`modules/orders/state-machine.ts:197`) after *every* item transition, purely as `deriveOrderStatus(item states)`. Two consequences:
1. A `packOrder` override that wrote `orders.status = "packed_partial"` directly would get silently clobbered back to whatever `deriveOrderStatus` says the next time any unit on that order changes state (e.g. a QC retry, a hold/release) — `recomputeOrderStatus` has no idea an override happened. This needed a real fix, not just a new enum value.
2. Adding a brand-new `ORDER_STATUSES` value at all has real consumer cost this wave: I found it hardcoded in `today/service.ts:28` (raw SQL literal list of open statuses) and referenced in `ai/assistant-tools.ts:112`, `invai-web/src/components/badges.tsx`, and both floor-unrelated `i18n/{en,es}.ts` files — none of those owners are on this wave, so CLAUDE.md's "a breaking contract change must be fixed in every consumer the same day" rule can't be honored for a new enum value right now.

Design (full Zod/shape in `wave.md` §"Contract stubs (exact)"): **no new `ORDER_STATUSES` value.** Instead, a new nullable `packOverride` field on `Order` (`{ reason, by, byName, at, missingItemIds }`, same shape as the existing `hold`/`cancel` nullable objects) backed by a new `orders.packOverride jsonb` column, and `recomputeOrderStatus` becomes override-aware: it still computes `deriveOrderStatus` first, but forces `status = "ready_to_ship"` (an *existing* value) when `packOverride` is set and the natural derivation would still be pre-ready, then clears `packOverride` once every unit is genuinely packed. This keeps every current `ready_to_ship` consumer (including the two above) correct with zero changes, at the cost of the order detail screen not visually distinguishing "genuinely all packed" from "packed with an override" until a web card picks up rendering `packOverride` — acceptable for this wave since no web card exists in wave 4 to do that rendering work anyway.

This required a named grant for T-4-1 into `db/schema/orders.ts` and `modules/orders/state-machine.ts`, both outside its normal `modules/production/**` boundary — added to the card, co-review by backend-foundation per the usual pattern for a one-off grant.

## Receiver permission design: new `production.receive` vs reusing `production.build`
Checked what `receiver` can call today: `purchaseOrders.receive` needs `purchasing.receive` (receiver already has it), `inventory.count` needs `inventory.count` (already has it) — both fine, `auth: "floor"` already allows a floor session. But `sheets.markReceived` needs `production.build`, which `receiver` has never had (`RECEIVER` in `roles.ts` has no `production.*` beyond `production.read`/`production.scan`). **T-4-3's "depends on" note claiming this procedure "already allows floor sessions" conflated auth mode with permission — the auth mode is fine, the permission is the actual gap**, and it's the one wave.md flagged correctly (a new `production.receive` permission, not full `production.build`).

Granting `production.build` outright to `receiver` was the easy option and the wrong one — that permission also covers batch preview/build, sheet regenerate, send-to-vendor and sheet cancel, none of which a receiving-desk role should touch. Went with the narrower design: new `production.receive` permission, granted to `receiver` and — since `sheets.markReceived`'s declared permission changes from `production.build` to `production.receive` rather than gaining a second allowed permission (the contract's `proc()` only takes one) — also granted to `office`, so office doesn't lose access it has today. `owner`/`admin` keep it automatically via `SHOP_ALL`. Full shape in `wave.md` §5; this is a deliberate permission reassignment on an existing procedure, not a pure addition, so I flagged it explicitly for `reviewer` to re-check nobody else loses access (nobody else had `production.build` who isn't already covered).

Also found: the backend's own `STATION_KINDS` enum (`db/schema/tenancy.ts:228`, currently `["pick","press","qc","pack"]`) is a separate list from the contract's `STATIONS` and does **not** pick up `"receiving"` automatically — a hidden dependency wave.md's original "Agreed interfaces" missed entirely. Named grant added to T-4-1 for that one line; T-4-1 should confirm whether `enumText` needs a migration for a new value or is an application-level check only.

## Outbox schema change: Dexie version bump and migration
Read `invai-floor/src/outbox/db.ts`. The card's premise ("outbox entries get `attempts`, `lastError` and `parkedAt`") is stale — `attempts` and `lastError` already exist on `OutboxEntry` (lines 24-25) from the current `version(2)` schema. Only `parkedAt: string | null` and a new `"parked"` value on `OutboxStatus` (currently `"pending" | "done" | "failed"`) are genuinely new.

Dexie only requires a version bump for schema-level changes — new tables or new **indexed** properties. `parkedAt` is a plain field, and `status` is already indexed (`outbox: "++seq, &id, status"`); Dexie doesn't validate index values against a TS union, so a new allowed string in an already-indexed field needs nothing either. **No version bump is required**, and no migration of existing queued entries is needed beyond a defensive one: pre-existing rows on paired tablets will read `entry.parkedAt` as `undefined` (the property never existed on them), not `null` — every read site must treat those the same, or a tablet mid-upgrade will show inconsistent "not parked" vs "parked: never" states. Documented this explicitly on T-4-2's card so it isn't left implicit. If T-4-2 later wants `parkedAt` indexed for the Problems Sheet query's performance, `version(3)` with `outbox: "++seq, &id, status, parkedAt"` is safe and needs no upgrade function — Dexie back-fills old rows with an undefined index key, which is queryable (just sorts/groups with the others under `undefined`).

## Hidden dependencies found
1. **`orders.status` stored-vs-derived mismatch** (above) — the biggest one; would have caused the override to silently disappear on the next scan.
2. **`STATION_KINDS` in `db/schema/tenancy.ts`** not covered by the contract's `STATIONS` stub — would have left `receiving` stations failing to register on the backend even after the contract and floor sides were done.
3. **`sheets.markReceived`'s actual permission gap** — T-4-3's card asserted this procedure "already allows floor sessions" as if nothing were missing; the permission (not the auth mode) was the real blocker, and reassigning it needed `office` to be re-granted in the same change or it would have been a silent regression for office staff.
4. **`wrong_style` is already fully shipped** (contract `MISMATCH_REASONS`, `matcher.ts:100`'s `compareBlank`, a passing `matcher.test.ts:71`, and both floor i18n catalogs, plus the generic `t(\`floor.mismatch.${result.mismatch}\`)` lookup already used in `PackStation.tsx` that needs no special-casing per mismatch reason). B-33 and the two cards' related acceptance criteria were rewritten as regression checks — building this again would have been wasted effort and a false "done" signal on a backlog item that's already closed in practice.
5. **`StationShell.tsx` and `src/app/db.ts`** — both above, under path overlaps.
6. **QC/bin idempotency today is a client-side heuristic, not server idempotency**: `invai-floor/src/outbox/outbox.ts:126-129`'s `isAlreadyApplied` guesses "already applied" from `INVALID_TRANSITION`/`CONFLICT` error codes rather than a real idempotency key, because `qc`/`assignBin`/`releaseBin` have none server-side today. T-4-1's real fix (an explicit `idempotencyKey`, matching the `ReceiveInput` convention already used elsewhere) makes that guess unnecessary going forward; flagged on T-4-1's card that narrowing/removing the client heuristic is a follow-up, not this wave's scope (T-4-2 doesn't own that logic change this wave).

No ADR needed for any of this — `packOverride` and `production.receive` are both extensions of existing patterns (nullable metadata objects like `hold`/`cancel`; scoped permissions like `purchasing.receive` vs `purchasing.manage`), not new architectural calls. The one genuinely new product decision (shipping an order short a unit) is the PM's to record, not mine.
