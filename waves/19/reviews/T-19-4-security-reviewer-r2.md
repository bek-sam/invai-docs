## Acceptance criteria (my scope: S-35, S-36, S-37, and the digest-email production default)
| # | Met? | Evidence |
|---|---|---|
| S-35: no token in any log line, including on an unhandled error, including via `app.onError` | yes | `links.ts` GET/POST bodies now run inside one try/catch each; on failure they log `{companyId, userId, kind}` (once `resolve()` succeeded) or nothing identifying (if it hadn't), never `c.req.path` or the token. Two new tests in `links.test.ts` prove both cases by spying on `console.error` and asserting the token string is absent. `app.onError`'s `loggedPath()` redacts any `/l/*` path to `/l/[token]` as defense-in-depth for a throw that reaches the framework handler directly (e.g. before `links.ts`'s own try, inside `limited()`) — correct by code inspection, not independently test-proven this round (see above) |
| S-36: mailer never logs the recipient address | yes | `sendMail`'s "mail sent" line now logs `companyId` and `toHash` (first 16 hex chars of `sha256Hex` of the lowercased, trimmed address), never `to: mail.to`. New `mailer.test.ts`: a real Mailpit send and an `"account"`-scoped send (no company) both assert the raw address never appears in `console.log` output, and that the company id and `"mail sent"` still do (support/ops can still correlate a send without the log holding PII) |
| S-37: the per-IP `links` bucket isn't trivially bypassable by spoofing `X-Forwarded-For` | met, as scoped | `clientIp()` now requires a single, well-formed IP (`node:net.isIP`) from `X-Forwarded-For`/`X-Real-IP`; a non-IP string, a forged multi-hop chain, an out-of-range dotted quad, or an injection-shaped string all collapse to the same `"unknown"` bucket a request with no header at all already uses — proven by two new tests, including one asserting the *exact* rate-limit key string (`tb:links:unknown`) is identical for spoofed and header-less requests. This closes the "any string buys a private bucket" bypass. It does **not** close the full trusted-proxy gap (a real multi-hop chain behind a genuine ALB still needs `advanced.ipAddress.trustedProxies` configured against that ALB) — r1 already scoped that as non-blocking locally and tracked under S-30, and this fix doesn't claim otherwise (see commit message and round-2 report, both explicit about the remaining scope) |
| S-37 doesn't break sign-in rate limiting or real single-hop proxy setups | met | `clientIp()` is called only from `src/api/links.ts` (via `limited()`) and defined in `src/api/context.ts`; Better Auth's sign-in rate limiter has its own IP resolution and never calls it (confirmed by `grep`), so it structurally cannot regress sign-in limiting — and `auth.test.ts`'s 23 sign-in rate-limit tests (which do send `x-forwarded-for` with real IPs) all still pass. A real single, well-formed IP (with or without surrounding whitespace) and a real `X-Real-IP` both still resolve correctly, matching what a normal client or a single reverse-proxy hop sends |
| Digest email production default | met | `DIGEST_EMAIL_ENABLED` lost its static `.default("true")` in the Zod schema (now `.optional()`) and is resolved in `env.ts` as `raw.DIGEST_EMAIL_ENABLED ?? !isProd` — `false` in production, `true` in dev/test, an explicit env value always wins. Four new subprocess-boot tests in `env.test.ts` cover: prod with no override (`false`), prod with explicit `true` (`true`), dev with no override (`true`), dev with explicit `false` (`false`) |
