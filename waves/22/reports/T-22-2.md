## Built
- **49 tenant-to-tenant FKs are composite** `(company_id, <col>) -> parent(company_id, id)`; 18 parents gained a
  `(company_id, id)` unique key through the new `tenantKey("<table>", t)` helper (files:
  `invai-backend/src/db/schema/_shared.ts`, `{ai,catalog,channels,finance,inventory,market,orders,personalization,privacy,production,shipping,tenancy,vendors}.ts`).
  References to `users` and `companies` (global identity tables) stay single-column, as the card and the
  architect's review scope them.
- **Migration 0030** (`drizzle/0030_foundation_composite_fks.sql`): `SET LOCAL lock_timeout = '5s'`, drop the 49 old FKs,
  add the 18 unique keys, add the 49 composite FKs `NOT VALID`. Nullable references keep their semantics with
  `ON DELETE SET NULL (<col>)` (PG 15+): a plain composite `SET NULL` would null `company_id`. drizzle emitted the
  FKs *before* the unique keys they need and cannot express the column list, so the generated file was reordered and
  edited by hand before it was applied anywhere (the snapshot is untouched; `pnpm db:generate` after it reports no
  drift). **Migration 0031** (`0031_foundation_composite_fks_validate.sql`): `VALIDATE CONSTRAINT` x 49 under the same
  lock guard; a real cross-tenant row fails and rolls back the run (architect A6). Today drizzle applies both in one
  transaction; in a rolling deploy they are two deploys (expand, then validate).

## Decisions
- **Composite FK names** `<child>_<col>_fk` and unique keys `<parent>_company_id_id_unique` (the digest module's
  existing pattern), declared with drizzle `foreignKey()` + `tenantKey()` rather than a wrapper helper, so the
  typechecker still verifies which table each column belongs to. Recorded in `src/modules/README.md` rule 5.
- **SET NULL column list in hand-edited SQL** (PG 15+; local is 17.11, RDS 17 supports it). The alternative, dropping
  SET NULL for `restrict`, would change delete semantics on scans/bins/sheets; rejected.
- **0030/0031 as two files** so a real deploy can run expand and validate separately once the migrator stops
  batching pending files; today both run in one transaction (documented in the SQL header).
- **Stall values.** BullMQ renews a running job's lock every `lockDuration/2`, so job duration (p95 or otherwise)
  never causes a stall; a stall means a dead worker or an event loop blocked past `lockDuration`. `lockDuration`
  therefore covers the longest *synchronous* stretch a handler can hold the loop (CSV parse of a large export,
  nesting bookkeeping: well under 10 s in the parser tests) with a wide margin, scaled by the queue's SLO budget
  (label < 60 s, compose < 5 min, research 11 §5.3); `stalledInterval` is 30 s where a person waits (sync, ship,
  ai) and 60 s where a re-run is expensive (render, reports). `maxStalledCount: 1` everywhere: one re-run (every
  handler is DB-idempotent, `idempotent-job`), then the failed set. No scale-run p95 per job exists: the `jobs`
  table has no started/finished timing and `qa-report.md` records only `buildDigest` 330 ms. If QA's next scale
  run shows a handler blocking the loop for longer, raise that queue's `lockDuration` (one line).
- **Trigram indexes dropped from the card's deliverable** (AC5), see Known gaps. Nothing else in scope was
  widened; the 0001 tenant-less trigram indexes were left as they are (a separate decision).

## Known gaps and follow-ups
- **AC5 cannot be met as written; needs an architecture decision (owner: architect, tech lead).** I built
  `(company_id, name gin_trgm_ops)` GIN indexes (with `btree_gin`) on orders, order_items and designs, migrated the
  copy, and `EXPLAIN (ANALYZE)` as `invai_app` under `withTenant` on the seeded copy plus 50,000 synthetic orders
  with random order numbers: `Seq Scan on orders … Filter: (company_id = … AND (order_no ~~* '%04000%' OR …)) Rows
  Removed by Filter: 50348, 24.8 ms`. With `enable_seqscan = off` and `enable_indexscan = off` the planner still
  only used the GIN for `company_id` (`Bitmap Index Scan … Index Cond: (company_id = …)`, the ilike stayed a
  `Filter`). A plain single-column probe index behaved the same for the app role, while **as the owner role the same
  probe index is used** (`Bitmap Index Scan on orders_order_no_trgm_probe, Index Cond: (order_no ~~* '%04000%')`).
  Cause, confirmed in `pg_proc`: an RLS policy is a security barrier and only leakproof operators may be evaluated
  as index conditions ahead of it; `textlike`, `texticlike`, `similarity_op`, `ts_match_vq`, `arraycontains` are
  `proleakproof = f`; `texteq`, `uuid_eq`, `starts_with` are `t`. Consequences: (a) the three 0001 trigram indexes
  on orders/order_items/designs have never served a request and cost writes on the hottest tables; (b) research 11
  G17's fix (tenant-leading GIN) is void under RLS; (c) shipping the five new indexes would have added dead weight,
  so they are not in 0030. Options for the architect: accept per-tenant sequential filtering (25 ms at 50k orders
  for one shop, bounded by `company_id` btree), switch the search to a leakproof-friendly shape (prefix `^@` with
  SP-GiST, or exact `=` on a normalized column), or an external search index. `LEAKPROOF` wrapper functions need a
  real superuser (not available on RDS). Proposed backlog row and lesson below.
- Existing tenant-less trigram indexes (`designs_name_trgm_idx`, `order_items_channel_sku_trgm_idx`,
  `orders_order_no_trgm_idx`, `listing_variants_channel_sku_trgm_idx`): candidates to drop in the same decision.
- **Two order-dependent flakes in the full suite, outside my paths** (green alone, red under parallel workers):
  `src/integrations/vendors/mailer-subject.test.ts` "keys the hash (S-38)" (`expected '2c138a…' not to be '2c138a…'`:
  the keyed hash equalled the plain sha256, which looks like the hash key env var being unset or overwritten by
  another worker; owner integrations-engineer, T-22-3) and `src/modules/market/service.test.ts` "refreshDemand…"
  (`expected '1970-01-01T00:00:00.000Z' to be '2026-09-15T16:00:00.000Z'`: a fake clock or `Date` epoch leaking
  between tests; owner backend-engineer, market). Neither existed in the first run and neither touches migrate,
  queues, worker options, tenancy or the FK schema. For the tech lead to route.
- The `updateOrg` audit `data` stores the raw input (as before); no PII there.
- The unique keys `(company_id, id)` are btree indexes on 18 tables: small write cost, created in-transaction
  (pre-launch, architect A5).
