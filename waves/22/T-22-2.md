## Acceptance criteria
1. Every FK from a tenant table to another tenant table is composite `(company_id, <fk>) → (company_id, id)` (as `digest.ts` does), with the needed unique `(company_id, id)` indexes; the migration is expand-safe (`NOT VALID` then `VALIDATE`, `lock_timeout`), and runs on the seeded dev copy in < 60 s. If `VALIDATE CONSTRAINT` finds a real cross-tenant row on the seeded copy, stop: report the rows (ids only) to the tech lead and security-reviewer; don't delete data (architect A6).
2. A new test fails if any tenant-to-tenant FK is not composite (introspects `pg_constraint`), and a test proves a cross-tenant reference insert is refused.
3. `migrate.ts`: the advisory-lock wait runs with `SET LOCAL statement_timeout = 0` and `lock_timeout` set (value in the report), so it never inherits the 5-min role timeout (B-163).
4. Workers set explicit `lockDuration`, `stalledInterval` and `maxStalledCount` per queue (values justified by the longest job's p95 from the scale runs); a test covers a stalled job being retried once, not twice (B-166).
5. Tenant-leading trigram indexes for the text searches the web uses (orders search, designs search): `(company_id)` + `gin_trgm_ops`; `EXPLAIN` on the seeded copy shows the index used (B-37 index part). Plain `CREATE INDEX` is fine pre-launch: drizzle runs migrations in one transaction, so `CONCURRENTLY` isn't possible (architect A5).
6. `me.updateOrg` (tenancy, contracts 0.8.0) stores and returns `shipsSaturday` and `transferAgeWarnDays`, with tests (added 2026-09-29 from T-22-1's report).
7. All backend tests green; RLS coverage green.
