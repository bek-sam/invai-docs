## Verdict: **approve with clarifications** (applied to `wave.md` and the cards)

## Contract stubs
Written into `wave.md`'s new "Contract stubs (exact)" section, 7 in total. Four were named in the plan's "Agreed interfaces" one-liners and needed exact shapes (`inventory.purchaseOrders.markPlaced`, the `printsInHouse`/`SHEET_TRANSITIONS` pair, bin/blank labels, `ai.listings.exportCsv`); two more I found missing entirely while checking each card's ACs against what the contract actually has today (`production.reprints.reasonsByWeek`, `finance.exportCsv` for profit); one is a bin-schema gap (`Bin` has no `id`-addressable name/archive lifecycle today) folded into the labels stub. All additive — new procedures, new optional fields, one appended `SheetState` enum value, two new nullable columns on `bins` — nothing renamed or removed, so no `contract-deprecation` process triggers.

One correction to the plan's own wording, applied throughout: "return PDF file ids" (`wave.md`'s original agreed-interfaces line) doesn't match this codebase's convention. There is no files table or file-id concept — every existing file reference (`GangSheetDetail.files.pdfKey`, `files.downloadUrl({ fileKey })`) is a raw S3 **key** string. I specified `{ key: string }` everywhere instead, so builders don't invent a parallel file-reference mechanism.

## In-house print state design (`SHEET_TRANSITIONS`, `printsInHouse`)
Architecturally sound as an additive state-machine change: insert `printing` between `ready` and `printed`, with `ready → [sent, printing, building, cancelled]` and a new `printing → [printed, cancelled]` row. `printed` already fans in from three predecessors (`sent`, `acknowledged`, now `printing`) with no change needed to its own outgoing edges, and downstream consumers (floor's `B:`/scan matching, shipping) key off `printed`/`shipped`/`received`, not the path taken to get there — so units flow to the floor exactly as today once a sheet reaches `printed`.

Two real gaps the card's one-liner didn't surface:
1. **The company setting has nowhere to live yet.** `CompanySettings` (`invai-backend/src/db/schema/tenancy.ts:79`) is a jsonb column with an existing shape (`riskWindowHours`, `onboardingDismissedAt`, etc.) — adding `printsInHouse?: boolean` there is free (no migration). But there is **no public read/write surface for it today**: `me.updateOrg` (`contract/tenancy.ts:33`) only accepts `name`/`timezone`. Exposing `printsInHouse` means touching `invai-contracts`'s tenancy schema/contract and `modules/tenancy/service.ts` — all outside T-6-2's owned paths and squarely inside T-6-5's this wave. I did not resolve this by fiat; I flagged it on both cards as needing either a T-6-5 favor (it's already in tenancy for the demo fix) or an explicit narrow grant, coordinated so the two concurrently-building cards don't collide on the same lines.
2. **Adding `printing` to `SheetState` breaks a file T-6-2 doesn't own.** `invai-web/src/components/badges.tsx:28`'s `SHEET_TONE: Record<SheetState, Tone>` is a plain typed object literal — TypeScript requires every enum key be present, so `tsc` fails the moment the enum grows, and that file is outside `routes/_app/production/**`/`features/production/**`. Flagged as a one-line grant.

I checked for other exhaustive `SheetState` consumers before concluding this was the only breaking one: `invai-web/src/routes/_app/vendor/index.tsx` and `invai-backend/src/modules/vendors/service.ts:536` both key by `SheetState`, but they're vendor-portal-scoped, and an in-house sheet never reaches a vendor-visible state (`printing` is only reachable from a vendor-free `ready`) — so these two are very likely fine as-is, but worth a quick look at build time rather than treating my read as certain.

## Where label rendering belongs (imaging vs. a backend PDF)
Imaging, matching existing precedent — this wasn't a close call once I checked what's actually installed. `invai-backend`'s `package.json` has `pdf-lib` (used in `shipping/service.ts` only to *merge* already-rendered label PDFs, not to draw anything), and no QR-code library at all. `invai-imaging` already has `qrcode` (Python) and already composes QR codes onto gang sheets in `app/compose.py`, plus a precedent single-purpose label endpoint (`POST /labels/mock`, `app/labels.py`, for the mock carrier's shipping label). The stub adds a sibling endpoint (e.g. `POST /labels/qr`) rather than teaching Node how to draw QR codes it has no library for. This confirms the wave's own plan ("imaging renders `BIN:`/`B:` QR labels") was already the right call — I just made the interface exact and named where it slots in next to the existing code.

## `exportCsv` format per marketplace
Read `modules/ai/service.ts:650`'s current `exportCsv(channel, c, sku)` closely, since B-101 already flags line 792's placeholder SKU. Two things the card's AC2 didn't spell out:
- **The function is per-draft, per-single-SKU today; the card wants `{ draftIds, channel }` with one row per variant.** That's a signature change, not a tweak — `(channel, content, sku)` → `(channel, rows: { content, sku }[])`, fed by joining each draft's `designId`/`productId` to `catalog.variants` (the same table T-6-1 reads as `BlankSummary` for real SKUs). Specified exactly in the stub.
- **Shopify has no branch at all.** The function has an `if (channel === "etsy")` branch and an `if (channel === "amazon")` branch; everything else — including Shopify — falls through to a generic fallback shape (`title/description/price/sku/tags/bullets`) that isn't Shopify's product-CSV format. The card's "Etsy first, then Shopify" phrasing reads like Shopify support already half-exists; it doesn't. Flagged on the card as new work: a proper `Handle`/`Variant SKU`/`Variant Price`-per-row branch.

This also finishes B-101's line-792 fix for free: once the function's contract requires real SKUs as input (not an id slice), there's no code path left that can fall back to `DRAFT-${id.slice(0,8)}`.

## T-6-5's guard coverage — every real-provider path, by adapter factory
This is where the plan's stated ownership is narrower than its own acceptance criteria. I grepped every adapter-factory function's call sites across the backend, not just the files the card lists.

**`isDemoCompany()` (`modules/tenancy/demo-flag.ts`) is exactly AC1's bug** — it reads `companies.demo` instead of `demoOwnerUserId IS NOT NULL`, confirming the card's own description. But it has **exactly one caller in the entire backend**: `modules/channels/service.ts:369`, Shopify's connect-time provider choice (this is the same gap wave 5's plan review flagged and recommended fixing — the fix apparently landed as a column-checking function with a single wired-up caller, not a comprehensive guard). Fixing the column alone does not give every real-provider path a live guard:

- **Carrier — the most exposed gap.** `carrierAdapter()`/`carrierTracking()` (`integrations/carriers/index.ts`) take no company argument at all; they choose mock vs. live from one process-wide `env.mocks.carrier` flag. There is no per-company hook to add without either (a) changing the factory's signature and updating all 5 call sites (`shipping/service.ts` ×4, `shipping/jobs.ts` ×1 — none owned by T-6-5), or (b) some ambient context this codebase doesn't have (`withTenant` wraps a DB transaction, not a JS-level context propagated to arbitrary function calls). This needs an explicit decision before build starts, not left implicit in "owned paths."
- **Marketplace/channels — 9 call sites, 4 files, 1 owned.** `getChannelAdapter()` (`integrations/channels/index.ts`) is called from `modules/channels/service.ts` (owned, 3 sites), `modules/channels/sync.ts` (3 sites), `modules/inventory/availability.ts` (2 sites), and `modules/ai/service.ts:732` — the AI-listings publish path, which is also exactly B-101's dead-branch line this same wave is fixing. None of the last three files are in T-6-5's owned paths. My recommendation, applied to the card: put the live demo check inside `getChannelAdapter()`/`webhookAdapter()` itself — one small owned file — rather than chasing every caller. That's both cheaper than a multi-file grant and closes the AI-publish gap without T-6-5 needing to touch `modules/ai/service.ts` at all, which would otherwise be an awkward two-card collision in the same file T-6-4 is rewriting this wave.
- **Blank suppliers aren't in the AC at all.** `getSupplierAdapter()` (`integrations/suppliers/index.ts`) goes live on a company's own S&S credentials (`modules/inventory/service.ts`), independent of demo status. I flagged this as a scope question for the PM/owner rather than silently adding it to T-6-5's build — the card as written doesn't promise this path, but the risk is identical in kind to carrier/marketplace.
- **Auth-notice email is subtler than "add a check."** `sendMail()` (`integrations/vendors/mailer.ts`, owned) is a genuine single choke point — `lib/auth-mail.ts` already routes through it, so a guard there would cover invites, vendor mail and auth notices in one place. But `sendMail()` currently takes no company/demo context, and its only caller with that context is `invites.ts`; auth notices originate in `auth.ts`'s Better Auth hooks with just a `user`, and a user can belong to more than one company (real + demo). I did not prescribe an answer — I flagged that "which company's demo status gates a user-level auth email" is a real design decision, not a mechanical wiring task, and it needs to be made explicitly before implementation, not discovered mid-build.

None of this changes the card's acceptance criteria in substance — "nothing real for a sample workspace" is still exactly right as a bar — but the owned-paths list as originally written could not actually clear that bar. I added the grants/design notes needed to close the gap to the card directly.
