## AC0: hypothesis — NOT REPRODUCED, numbers first
Real dev DB (40 seeded designs) + real worker (`render` queue, concurrency 2), imaging stubbed at
a realistic ~250ms/call (same for old/new, clean A/B). `production.scan` = floor.ts `scan` called
directly, read-only miss path.

| Scenario | n | p50 ms | max ms | `idle in transaction` |
|---|---|---|---|---|
| Idle | 30 | 6 | 45 | 0 |
| OLD code: one tx held across all of a design's preview calls, 40-job burst | 40 | 15 | 51 | **2, confirmed throughout the ~5.3s burst** |
| NEW code (this fix), same burst | 40 | 14 | 38 | 0 |

Mechanism is real (2 sessions genuinely "idle in transaction", matching concurrency) but doesn't
slow `scan` beyond jitter — nowhere near the gate's 10s timeout in this setup. **Not reproduced**,
corrected from this report's original "refuted" per reviewer r1 finding 3: `scan` was called
directly on the read-only miss path, not over HTTP with a station token the way the floor client
does it; imaging was a 250 ms Node stub, not real imaging under CPU load; and the "OLD" side was a
standalone script replicating the removed code path, not the committed code running live. Those
gaps mean this measurement can rule the mechanism out for the paths and load it actually exercised,
but not for the floor's real HTTP scan path under real imaging contention — "refuted" overstated
what was shown. API and worker are separate processes with separate Postgres pools;
`renderDesignPreviews` only touches `design_files`, which `scan` never reads, so the mechanism is
unlikely to reach the HTTP path either, but that's inference, not measurement. Built AC1–AC3
anyway (B-233 debt). Next suspect: Redis is shared between BullMQ and the realtime pub/sub `scan`
uses after commit — a real cross-process resource, unlike Postgres pools here.
