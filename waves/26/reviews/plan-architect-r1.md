# Plan review: waves 26 + 27 (AI listing photos), architect, round 1
Reviewer: architect (opus). Author: tech-lead. Read: both wave.md files, T-26-1..5, T-27-1..5, ADR 0022, code cited below.
**Verdict: changes-required.** The overall design holds: design pixels only ever go through invai-imaging, the ownership fences don't overlap (each file has one owner at a time, and T-26-4/T-27-3 and T-26-3/T-27-1 run one after the other), and the grants are one line each. Fix the 9 items below in the cards, then I approve without another round of reading code.

## Blocking (card: exact change)
1. **Rate buckets: a grant is missing (lesson W23).** `bucketFor` (invai-backend/src/api/orpc.ts:186-195) sends only `path[0]==="ai"` to the `ai` bucket. `photos.analyzeDesign`/`createSet` spend credits but would land in `writes`. Any non-GET `photos.read` procedure (for example `estimate` as POST) fails buckets.test.ts:151-178 until it is classified. **T-26-4:** add grants for `src/api/orpc.ts` (one set routing `photos.analyzeDesign`, `photos.createSet` and, in wave 27, `photos.pushToShopify` to `ai`, plus any NON_GET_READS line) and for `src/api/buckets.test.ts` (matching lines). **T-26-1:** list each procedure's method and bucket in the ADR.
2. **The new namespace breaks backend typecheck until it is mounted.** `src/api/router.ts:39-64` must name every contract key. Once T-26-1 commits, `pnpm typecheck` in the backend stays red until T-26-4 lands, so T-26-3's full check fails. **wave.md step 3:** right after T-26-1, T-26-4's owner commits `modules/photos/router.ts` (all stubs) and the router.ts mount line before T-26-3 runs its final suite.
3. **The credit kind is missing from the contract card.** `ai.credits.ledger` returns `r.kind` from the backend ledger (modules/ai/service.ts ~1489) through the contract enum `CREDIT_KINDS` (invai-contracts/src/schemas/ai.ts:233). A `photo_image` row then fails output validation. **T-26-1:** append `photo_image` to the end of that enum. **T-26-3:** add the mirror line (db/schema/ai.ts:175). **T-26-5:** add `creditKind.photo_image` to en.ts:645, es.ts and scripts/i18n-es.json:541 (the billing table falls back to raw text, billing.tsx:480).
4. **Analysis: request or queue? The cards disagree.** T-26-1 AC4 says the queue. T-26-4 AC2 says "calls … and returns it". `analyzeDesignForPhotos(tx, ctx, …)` would also hold a DB transaction open across a vision call. The precedent goes the other way: `createDrafts` enqueues with `afterCommit` (service.ts:273), and `generateDraft(companyId, draftId, userId)` runs with no transaction (service.ts:450). **Change the interface to** `analyzeDesignForPhotos(companyId, userId, input)`, run in a job on the `ai` queue. `photos.analyzeDesign` returns the cached result, or enqueues and returns `{status:"pending"}`. Update T-26-4 AC2 and T-26-5 AC3 (poll until ready).
5. **The credit guard isn't named, and the unit is mixed up.** `chargeCredits` (src/ai/credits.ts:63-90) is a plain insert, and `ai_credit_ledger` has no unique key (db/schema/ai.ts:203-217), so a ref alone doesn't make the charge idempotent. T-26-4 AC4 charges "per composition" but sets "ref = the image id", and a composition has one image per channel. **T-26-4 AC4:** the charged unit is a composition row (set, garment, view, hex). Guard: `SELECT … FOR UPDATE` on that row plus `charged_at IS NULL`, then charge and set `charged_at` in the same transaction. ref = `{type:"photo_composition", id}`. **T-27-3:** the same guard per scene image (`photo_scene`). Optional belt and braces: T-26-3 adds a partial unique index `(company_id, ref_type, ref_id) WHERE ref_type LIKE 'photo_%'`.
6. **Disclosures never reach the export, and their storage is unsafe.** `exportCsv` appends only `content.disclosures` (service.ts:771). No CSV carries images: Shopify `Image Src` is blank (service.ts:854). `regenerateDraft` rebuilds `content` through `toContent` (service.ts:382-396), which would wipe anything stored there. **T-26-3 AC5:** store image disclosures in a new `listing_drafts.image_disclosures` column. Its migration is generated before T-26-4's; write that order in wave.md. Add a separate en/es `IMAGE_AI_DISCLOSURE` ("some product photos are AI-generated scenes; the design is ours") to the Etsy description when `aiGenerated`. Do not reuse `AI_DISCLOSURE`. **ADR 0023:** CSVs carry no image URLs (keys aren't public), so images leave only by zip or Shopify push.
7. **`productRef` has no source to pick from.** The channels contract has no product or listing shape, but the backend has `listings` (db/schema/channels.ts:96-124: connection, `channelListingId`, `designId`). For Shopify, `channelListingId` is the legacy product id (shopify/common.ts:251, orders.ts:181; mock 8_100_000_000+n, mock.ts:53). **T-26-1:** `productRef = {listingId: Id}`, checked as same company, same `connectionId`, channel shopify. Add `photos.pushTargets {designId, connectionId?}` (GET, photos.read) returning Shopify listings, this design's first. **T-27-3** implements it (a read of `listings` as a tolerated foreign-table read, with a doc comment) and maps it to `gid://shopify/Product/<id>`. **T-27-4** takes that gid. Without this, T-27-5 AC5 can't be built.
8. **Phase B as written won't survive the real provider.** OpenAI documents GPT Image masks as prompt guidance only: the model may re-render the whole image, and its edit sizes are 1024², 1536×1024 and 1024×1536. So check 1 ("print region pixels unchanged") will fail most real outputs, and the base's `print_box_px` may no longer line up. **T-27-2:** check 1 becomes "garment outline aligned". Compare an edge map in a ring around the print box after registering output to base, restore the base's blank print-box pixels before compositing, then run check 2 as written. Upscale from provider size to the preset, documented (Etsy ≥2000 px). **T-27-1:** confirm mask semantics, sizes and `input_fidelity` in `node_modules/openai` (7.25) and the docs, and make the mock also perturb the whole frame slightly so these paths get tested. **ADR 0023** records the approach.
9. **Render fairness on the golden path.** The `render` queue has concurrency 2 (lib/queues.ts:23-25). One 48-composition set job running about 240 renders at roughly 1.5 s each holds a gang-sheet slot for about 6 minutes. **T-26-4 AC4:** one job per composition, with a lower `priority` than sheet compose. **T-26-2 / T-27-2:** add `/photo/render` and `/photo/scene-composite` to `HEAVY_PATHS` (invai-imaging/app/guard.py:23).
