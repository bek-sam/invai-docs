## Acceptance criteria
1. **Template library, drawn in-repo.** Tee, hoodie, crewneck and tank, each with views `front_flat`, `folded`, `back` and `on_model_white` (a drawn, neutral figure wearing the garment on white). All drawn by code (bezier paths like `mockups.py`) or generated by a script committed to the repo; no downloaded stock images or fonts with unclear licences. Each template defines its physical scale (pixels per inch at the master size) and print areas (front and back, in inches, realistic: adult tee front ~12×16 in max, hoodie front above the pocket, tank narrower), plus a print-area mask and shading/displacement maps (folds and shadows visibly bend and darken the print, like the existing tint maps).
2. **Real size, real color.** Given a design file of W×H inches and a garment template, the composite places the design at exactly W×H inches on the template's scale, centred at the template's placement anchor, never scaled up to fill. A design larger than the print area is scaled down to fit and the response says so in `checks.failures` (`design_larger_than_print_area`). The blank is filled with the exact `blank_hex` (sample the flat, unshaded garment pixel in a test: it equals the hex). `back` uses the back print file; without one the backend skips that view (document it).
3. **White underbase preview.** With `underbase_preview: true` on a dark blank (luminance below a documented threshold), semi-transparent design pixels show over white underbase instead of the blank color, matching how DTF prints. On light blanks it changes nothing. Test both.
4. **Presets and automated checks.** For each preset in `wave.md`, the output meets size, aspect, format (JPEG sRGB or PNG as documented) and background rules, and the response's `checks` reports: `background_pure_white` (every pixel outside the product mask is exactly RGB 255,255,255 after encoding; for `amazon_main` this must pass), `fill_ratio` (product bounding box share of the frame; `amazon_main` ≥ 0.85), `longest_side_px` (`amazon_main` ≥ 1600; `etsy` ≥ 2000). A failed rule sets `passes: false` with a code. Templates marked `drawn` set `checks.failures` to include `illustration_not_photo` for `amazon_main` only (Amazon wants a photograph for the main image; compliance-officer confirms the wording of the rule in the review).
5. **XMP keywords.** When `xmp_subjects` is non-empty, the saved file carries them as XMP `dc:subject` keywords (test: read the file back and find `contains-synthetic-performer`). Empty list: no XMP packet added.
6. **Palette.** `/photo/palette` returns up to 6 dominant colors with shares that sum to about 1 over opaque pixels, plus `light_share`, `dark_share`, `transparent_share`. Deterministic for the same file.
7. **Zip.** `/photo/zip` writes a zip (Python stdlib, no new dependency) of the given keys with the given names to `out_key`; names are sanitised (no `..`, no absolute paths); every key must be in the same company prefix as `out_key`, otherwise 400.
8. **Safety and budget.** All routes require the shared secret; every input key and `out_key` passes the existing company-prefix check; inputs obey the existing pixel caps (`limits.py`); `/photo/render` and `/photo/zip` are added to `HEAVY_PATHS` in `app/guard.py` (~line 23) so they share the concurrency guard (plan review item 9). Budgets in the report: render time per image at 2000 px (target under 1.5 s on this Mac), peak RSS per render (target under 400 MB), zip of 48 images. Templates are cached per size.
9. Look at the output: save one contact sheet of all 16 template views on a black and a white blank with the seed's sample art, open it, and attach the path (not the image) in the report. Honest note in the report: drawn "on model" figures are illustrations, not photoreal.
