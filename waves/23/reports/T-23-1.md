## Known gaps and follow-ups
- **AC9 Spanish alert text — blocked, needs a backend/contract owner.** `Alert`
  (`invai-contracts/src/schemas/alerts.ts`) has no `data` field, and `toAlert()`
  (`invai-backend/src/modules/today/service.ts`) doesn't return one; oRPC's output validation
  (`schema["~standard"].validate`) strips unknown keys, so `data.titleEs`/`data.messageEs`
  (written by `vendors/delivery.ts`) never reach the client regardless of web code. Fix needs an
  optional `data: z.record(...)` on `Alert` (architect) and `toAlert()` to pass it through
  (backend-foundation or vendors owner).
- i18n regeneration surfaced **384 pre-existing keys with no Spanish translation** in
  `i18n-es.json` (falls back to English; e.g. `reprints.*`, `adSpend.*`, several `billing.*`/
  `digests.*` keys, visible in screenshots 05/07/08/09). `i18n-es.json`/`en.ts`/`es.ts` had drifted
  out of sync with actual `t()` calls before this card touched anything (en.ts was missing
  `action.add` etc. that source already called with a default). Reported for a reconciliation card;
  translating all 384 is out of this card's scope/budget.
- Resend-email button can't be scoped to `unknown`/`failed` deliveries specifically (same missing
  API surface as AC9 above); shows whenever a sheet was sent by email.
- `SignedImage` has no `<img onError>` fallback (only handles its own RPC call failing); harmless
  in real use (dev CSP/https S3 both load fine), only visible when testing a prod-CSP `vite
  preview` build against local http MinIO (img-src blocks it). Not touched — shared component,
  pre-existing, out of scope.

**1. Spanish regression (reviewer r1, blocking).** Root cause: `i18n-es.json` had silently drifted
out of sync with the hand-edited `es.ts` for a long time (374 keys) and never had 91 keys that are
only reached via `tr(...)` (a bare `i18n.t` alias the extractor's `t("key","default")` regex
doesn't match) or a dynamic template key. Fix: flattened `en.ts`/`es.ts` at `54b64d7` with a small
script (Node's built-in TS type-stripping importing the generated files directly — no new tooling)
and restored every Spanish value into `scripts/i18n-es.json` (2015 keys), added the 91 dropped
keys' English defaults to `scripts/i18n-extra-en.json` grouped by prefix (assistant.tool.*,
billing.*, creditKind.*, digest.costLine.*/emailSkip.*/feedback.*/glance.*/settings.*/source.*,
errors.*, market.band.*, profit.refundSource.*, reprintStatus.*, ship.exportWhere.*, etc.),
restored their Spanish too, and additionally translated 10 keys that had never had Spanish at all
before this wave (`action.add/cancel/close/next/save`, `common.loading/noResults`,
`adSpend.subtitle`, `po.markPlacedHint`, `stock.submitCount` — real, pre-existing gaps, not part
of the round-1 regression). Re-ran `pnpm i18n`.
  - Proof (script, not eyeballed): 0 of the 1953 keys present at `54b64d7` are missing now.
    es==en count is exactly 39 — the same 39 keys as at `54b64d7` (loanwords/brand names: Etsy,
    Shopify, Amazon, TikTok, Walmart, eBay, API, PDF, mockup, demo, PIN, Regex, "color" as used in
    this domain, S&S/SanMar) — zero new ones. This card's own new Spanish (the 46 keys from
    round 1, e.g. scan forms, station maintenance, photo upload, company toggles) is untouched.
  - `scripts/i18n-es.json`, `scripts/i18n-extra-en.json`, `src/i18n/en.ts`, `src/i18n/es.ts`.

**2. Billing money in es-US (product-designer r1, blocking, AC6).** `billing.tsx`'s 3 `<Money>`
usages (this-period label fees, plan price, per-label fee) had no locale control (`Money` takes no
locale prop) and fell back to bare `i18n.language` ("es"), rendering "149,00 US$" — clashing with
the page's own `localeNumber`/`digestMoneyLang` es-US convention for counts. Switched all 3 to
`formatMoney(cents, "USD", digestMoneyLang(i18n.language))` from `@invai/ui`, wrapped in the same
`tabular-nums` span `Money` uses. Verified live (screenshot): "$149.00", "$349.00", "$699.00",
"$0.10 por etiqueta", "$10.48 en tarifas de etiquetas" — all es-US, no more comma-decimal mixing.
`Money` import dropped (unused in the file now). `src/routes/_app/settings/billing.tsx`.

**3. Shipping tabs at 390 px (product-designer r1, blocking).** The 4-trigger `TabsList` (added
"End of day") overflowed with no scroll affordance. Wrapped it in the same
`-mx-1 overflow-x-auto px-1` pattern `orders/index.tsx` already uses. Verified: no page-level
horizontal scroll (`document.documentElement.scrollWidth === clientWidth`), and scrolling the tab
strip itself reaches "Envío de rastreo" (the 4th tab). `src/routes/_app/shipping.tsx`.

**4. Photo-preview broken-image icon (product-designer r1, optional note) — checked, not this
card's bug.** Reproduced live: uploaded a photo to a template's photo slot on the preview build
(`vite preview`, port 5186) and the live-preview `<image>` fails to load with `net::ERR_BLOCKED_BY_CSP`
against `http://localhost:9000/...` (local MinIO). Cause: `vite.config.ts`'s `prodCsp` —
served by both `preview` and the real production build — sets `img-src 'self' data: blob: https:`
(no plain `http:`), which is correct for a real deployment (S3 is always HTTPS) but blocks local
MinIO, which is HTTP-only in this dev stack. That CSP line predates this card by 5 commits
(`5896ba5`, T-12-5, "Strict CSP and security headers"); T-23-1's only `vite.config.ts` change was
the unrelated vendor-chunk split (`d7029ff`). The upload flow, `SignedImage` and the SVG
`<image href=...>` preview all work correctly — this is a CSP artifact of testing a `preview`
build against local HTTP MinIO, not a code bug, and not owned by this card (CSP policy is a
platform/security concern). No file changed for this item.
