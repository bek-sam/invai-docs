## Round 2

Fixed all 5 blocking findings. Commit: `invai-infra` `3215fc6` (`scripts/gate.sh`,
`scripts/gate/lib.sh`; not pushed). `.claude/hooks/guard-bash.py` and
`.claude/hooks/tests/test_push_stamp.py` are outside git and updated in place.

### Finding 1: push detection now fails closed

`simple_commands` (`.claude/hooks/guard-bash.py`) now threads a tracked working directory through
its existing flattening pass: it starts at the session's own `cwd`, and updates on `cd`/`pushd`
(a literal target, absolute or resolved against the tracked dir; `popd` and any target containing
`$`/`` ` ``/`cd -` mark it `CWD_AMBIGUOUS`, a sentinel distinct from any real path). A
`bash -c`/`eval`/`$(...)`/backtick body gets its own copy of the cwd at that point and never leaks
its own `cd`s back out (correct subshell isolation - verified with `bash -c 'cd repo && push'`). A
leading `GIT_DIR=<value>` word is captured the same way `_strip_prefix` already captures other
prefixes. `_gate_check_push` resolves the push's target directory from `-C`/`--git-dir`/`GIT_DIR`
(highest precedence, chained in order like git itself) else the tracked cwd, and denies outright -
`can't tell which repo this push targets with certainty ... Run it as: git -C /abs/path/<repo>
push origin <sha-or-main>` - whenever that resolves to `CWD_AMBIGUOUS`. `invai-docs` is exempt
only once positively resolved to it (a plain `cd invai-docs && git push` with no stamp still
allows; a `for r in ...; do git -C $r push; done` still denies even with a fresh stamp for one of
the repos, since `$r` never resolves).

Evidence: 18 new tests in `TestPushStampRepoResolution` cover every bypass form from the review
(`cd repo && push`, `cd repo; push`, `(cd repo && push)`, `pushd repo && push`,
`bash -c 'cd repo && push'`, `GIT_DIR=repo/.git push`, `git --git-dir=.../repo/.git push`, the
`for r in ...; do git -C $r push; done` loop, `cd -`, `popd`), each proven both to `allow` with a
fresh matching stamp and to `deny` with a stale/missing one, plus a control case confirming a
genuinely unrelated cwd (`/tmp`, no repo anywhere) still falls through to the existing rules
unchanged.

### Finding 2: bash 3.2 compatibility

`scripts/gate.sh`'s no-arg default-repo path used `mapfile -t GATE_REPOS < <(default_repos)`;
`/bin/bash` on this machine is 3.2.57, which has no `mapfile`. Replaced with a `while IFS= read -r`
loop over the same process substitution, matching the earlier `bash32-empty-arrays` memory note
(guarding the empty case with `GATE_REPOS=()` declared up front, never a bare unguarded
`"${arr[@]}"` on a possibly-empty array).

Evidence: `pnpm gate` with no arguments (repo has real uncommitted changes to gate.sh/lib.sh at the
time, and multiple repos genuinely ahead of `origin/main`) ran past repo selection with no
`mapfile`/unbound-variable error and refused cleanly on finding 4's new dirty-tree check (exit 1,
one line, no crash) - proving the no-args path now runs instead of dying before it can print
anything.

### Finding 3: process-group start/stop

`start_dev_all` (`scripts/gate/lib.sh`) now runs `(cd "$INFRA_DIR" && pnpm dev:all)` under `set -m`
(job control), which makes the backgrounded job its own process-group leader (PGID = its own PID).
`stop_group` signals the *negative* PGID (`kill -TERM -- -$pgid`, then `-KILL` after a 5s grace
period) instead of the bare PID, reaching every descendant (`pnpm` -> `bash dev.sh` ->
`exec concurrently` -> api/worker/imaging/web/floor). `run_golden_path`'s restart step calls
`stop_group` then `remove_started_pid` before starting a fresh group; `cleanup`'s EXIT trap now
calls `stop_group` on every recorded id too.

Evidence: a standalone simulation (real `sleep`/`bash -c` processes) reproduced the reviewer's
exact scenario and confirmed a plain PID kill left survivors, then confirmed `set -m` +
negative-PGID kill leaves none. A second simulation bound the actual 4 golden-path ports
(3000/8000/5173/5174, one python http.server per port under the same group structure) through a
full start -> stop -> restart -> stop cycle and checked with `lsof -tiTCP:<port> -sTCP:LISTEN`:
all 4 free after the first stop, all 4 listening again (new PGID) after the restart, all 4 free
after the final stop. Did not run the real golden-path phase (out of scope this round; a gate slot
comes after review).

### Finding 4: start-SHA capture, dirty-tree refusal, end-SHA comparison

`check_clean_and_capture_shas` (new, `scripts/gate/lib.sh`) runs right after repo validation:
refuses the whole run (`GATE REFUSED`, one line) if any repo in scope has uncommitted tracked
changes (`git status --porcelain --untracked-files=no`), else records each repo's HEAD into a
global `START_SHAS` array (same index as `GATE_REPOS`). `write_stamp` now stamps a repo only if its
end-of-run HEAD still equals its `START_SHAS` entry *and* its tree is still clean; otherwise it
logs why and moves on (never crashes the whole write).

Evidence: `pnpm gate invai-contracts` (see below) captured `START_SHAS` and stamped normally on a
clean, unchanged tree. `pnpm gate` with no args refused with exactly `invai-infra has uncommitted
tracked changes; commit them first (gating a dirty tree could stamp a commit that was never fully
tested)` while this round's own edits were uncommitted - the refusal firing for real, not just in
a unit test.

### Finding 5: stamp compared against the pushed commit, not always HEAD

`_refspec_sources` (new) reads a push's own arguments for an explicit refspec's source
(`origin main` -> `["main"]`, `origin <src>:main` -> `["<src>"]`, no refspec -> `[]`, meaning
HEAD). `_gate_check_push` now `git rev-parse <src>^{commit}` in the resolved repo for each source
and compares *that* against the stamp, denying if it doesn't resolve or doesn't match, instead of
always reading local HEAD.

Evidence: new `TestPushStampRefspec` - `git push origin main:main` still allows with a fresh HEAD
stamp; `git push origin HEAD~1:main` denies (`stale`) even with a fresh HEAD stamp, since the
pushed commit is the parent, not HEAD; `git push origin no-such-branch-xyz:main` denies (`can't
resolve`).

### Known gaps / follow-ups

- `invai-docs/team/hooks/guard-bash.py` and `test_guard_segments.py`'s `B07` row still need
  syncing/updating by the tech lead (see above).
- The cwd tracker treats a literal `(...)` grouping as an ordinary sequence point rather than a
  true subshell scope, so a `cd` inside one is not un-done after its `)` for a *later* push in the
  same command. Every case this guard needs to catch has at most one push per command, so this
  never matters in practice, but it's a known simplification, noted in `simple_commands`'s
  docstring.
- `pushd`/`popd` are tracked as "go to this directory" / "give up", not a real directory stack;
  fine for denying (fail-closed), would need real stack tracking if a future case needed `popd` to
  resolve correctly rather than just refuse.
- Optional notes from the round-1 review (the stamp being forgeable by any allowed Bash write,
  `pnpm gate` silently wiping the shared dev DB for a non-QA caller, `write_stamp` dropping
  unrelated repos' entries, cosmetic `count_passed`/`failing_names`/`STARTED_PIDS` issues) were not
  in scope for this round's blocking findings and are unchanged.
