## Market answer: (b) — seed lacks data the badge needs
`invai-backend/src/modules/market/service.ts:437` sets the "own" source's `mock` flag to
`await isSampleWorkspace(ctx.companyId)`. Per `invai-backend/src/modules/tenancy/demo-flag.ts:11-22`,
Desert Bloom Tees (the seed's owner login) is **not** a sample workspace (`demoOwnerUserId` is
null, only per-user `tenancy.demo` companies and retired demos qualify) — so its own signals are
never `mock:true`. The only other way `mock` can flip true is an *outside* demand reading
(`invai-backend/src/modules/market/compute.ts:487` etc., rolled up in
`invai-backend/src/modules/ai/assistant-tools.ts:767` as `rows.some(r=>r.mock)||recs.some(r=>r.mock)`),
sourced from table `market_series_cache` (`invai-backend/src/db/schema/market.ts:55`), written only
by `refreshDemand()` (`invai-backend/src/modules/market/jobs.ts:97`). That job is enqueued only by
`marketSweep()` (`jobs.ts:557`, hourly scheduler `MARKET_SWEEP_EVERY_MS`, `jobs.ts:535`) or the
nightly `0 3 * * *` UTC cron (`jobs.ts:585`) — neither has fired on a stack just booted from a
fresh seed (`pnpm db:seed` never calls `refreshDemand`/`computeSignalsForShop` itself; "Market
trend" text appears anyway because `design.updated` events trigger `computeSignalsJob` for *own*
signals only, `jobs.ts:515`). **Precondition for backend-foundation (T-23-10):** table
`market_series_cache` needs ≥1 row per canonical query with `mock=true` before `/assistant`
E2E runs — i.e. run `refreshDemand()` once after seed (or shorten/force the sweep) so outside
demand data exists for company Desert Bloom before the market suite runs. Confirmed live: with a
fresh scratch seed + running API, "Sample data" never appears (`market.spec.ts:101` times out,
`element(s) not found`) while "Market trend" (own signals) renders fine — not fixed, not touched,
per card scope.

## Environment note (own mistake, fixed, documented for memory)
1. Ran `invai-backend`'s `pnpm db:reset` against the scratch DB `invai_seed_t239` without
   overriding `REDIS_URL`; the script also obliterates BullMQ queues (`src/db/reset.ts:91`) in
   whatever `REDIS_URL` is set, which defaults to the **shared dev Redis DB 0** — wiped
   `{"sync":33,"render":43,"ship":10,"ai":2,"reports":915}` queued jobs there. Postgres was never
   touched outside my own `invai_seed_t239` copy. From then on I pinned `REDIS_URL=redis://localhost:6379/13`
   for every backend command. Filed as a tooling gap: `db:reset` should require/derive its Redis
   scope from the target DB, not default to DB 0 (backend-foundation).
2. The card's prescribed `PORT=3139` for the scratch API cannot work with the web dev server:
   `invai-web/vite.config.ts:16,33` hardcodes the dev CSP's `connect-src` to
   `http://localhost:3000` only, not derived from `VITE_API_URL` (unlike the `build`/`preview` path,
   which correctly reads `process.env.VITE_API_URL`, `vite.config.ts:40-47`). Every browser fetch to
   :3139 was silently CSP-blocked, surfacing as "No podemos conectar con InvAI" on every `loginAs`
   call — not a real product or test bug, confirmed by: curl to :3139 working fine throughout,
   `import.meta.env.VITE_API_URL` correctly baked as :3139, and the failure disappearing entirely
   once I moved the scratch API to :3000 (free at the time, confirmed via `lsof`). Filed as a gap
   for web-engineer: parameterize `devCsp`'s `connect-src` from `VITE_API_URL` like `prodConnectSrc`
   already does.
3. `pnpm db:seed` also writes the shared `invai-backend/seed-output.json` (no `SEED_OUTPUT_FILE`
   override used) — backed up first, diffed after (identical, seed IDs are deterministic), restored
   to be safe regardless.

## Decisions
- Ran the scratch API on :3000 instead of the card's :3139, the only port the web dev server's CSP
  currently allows; :3000 was free (`lsof` confirmed) and no other agent's dev:api uses it. Filed
  the CSP gap above rather than editing `vite.config.ts` (not my owned path).
