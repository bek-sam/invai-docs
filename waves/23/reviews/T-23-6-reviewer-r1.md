## Blocking findings
1. `.claude/hooks/guard-bash.py:347-353` and `:366-367`: the repo is resolved only from the hook's `cwd` or a literal `git -C <dir>`. A `cd` earlier in the same command, `pushd`, a subshell, `GIT_DIR=`/`--git-dir=`, or `-C $r` with an unexpanded variable all resolve to the workspace root (no `.git`) or `invai-docs`, and `_gate_check_push` then returns `None` ("nothing of ours to gate"), which allows the push.
   - **Failure scenario:** the tech lead, whose Bash cwd is `/Users/bekbolsun/invai`, runs `cd invai-backend && git push origin main` (the form used in the team docs, and the only way an agent without a persistent cwd can push without `-C`) after a gate run that failed, or with no stamp at all. The guard allows it; untested code reaches `main`. The wave loop `for r in invai-backend invai-web; do git -C $r push origin main; done` is allowed the same way with no stamp. Probes in the evidence table.
   - **Fix:** fail closed once the command is a push whose repo can't be pinned. For example: resolve the repo from the last `cd`/`pushd` before the `git` word within the command (reusing the parser's command list), honour `--git-dir`/`GIT_DIR`/`--work-tree`, and deny when a `-C`/`--git-dir` value contains `$` or when the resolved directory is not inside a repo but the command text names an `invai-*` code repo. Simpler and stricter: deny a push unless the target is a literal `git -C <path>` or the cwd itself is the repo, and say so in the message. Add the probe forms above as tests, and change `test_unidentifiable_repo_falls_back_to_existing_rules` so it no longer locks in the fail-open path for a workspace-root cwd.
2. `invai-infra/scripts/gate.sh:38`: `mapfile` doesn't exist in bash 3.2, which is the only bash on this machine (`#!/usr/bin/env bash` and `"gate": "bash scripts/gate.sh"` both resolve to `/bin/bash` 3.2.57). With `set -u` the script then dies at line 47.
   - **Failure scenario:** the tech lead runs `pnpm gate` with no arguments, as AC1 and the README describe. It exits 1 with `mapfile: command not found` / `GATE_REPOS[@]: unbound variable` and prints nothing on stdout, so the default mode never works. (Reproduced above.)
   - **Fix:** a bash 3.2 loop, e.g. `GATE_REPOS=(); while IFS= read -r r; do GATE_REPOS+=("$r"); done < <(default_repos)`. Guard the empty-array expansions under `set -u` for bash 3.2 (`${GATE_REPOS[@]+"${GATE_REPOS[@]}"}`), and run the no-args path once as proof.
3. `invai-infra/scripts/gate.sh:82-84`, `:110-117`, and `scripts/gate/lib.sh:22-35`: the recorded PID is the `( cd ... && pnpm dev:all )` subshell. SIGTERM/SIGKILL to it doesn't reach `pnpm` → `bash dev.sh` → `exec concurrently` → the five app processes (my simulation of the exact sequence left all children running).
   - **Failure scenario:** in the golden-path phase, line 110 "restarts" the stack. The old api/worker/imaging/web/floor keep running and holding :3000/:8000/:5173/:5174. The second `dev:all` can't bind (vite may move to another port), but `wait_http_ok` succeeds against the *old* stack. The E2E suites then run against a worker that saw jobs from before the reset, which is the thing the restart exists to prevent. At exit the trap "stops" only the subshells, so the whole dev stack is left running. That breaks AC3 ("stops everything it started, even on failure"), and the next gate run refuses on the ports.
   - **Fix:** start the stack in its own process group and signal the group. For example, start it with `set -m` around the background launch (or `perl -e 'setpgrp; exec @ARGV'`, since `setsid` isn't on macOS), record the PGID, `kill -TERM -- -$pgid` and wait, then `-KILL`. Or record the listener PIDs on the four ports after startup (they belong to this run, because the ports were free at the start) and stop those too. Prove it with `lsof -iTCP:3000 -sTCP:LISTEN` empty after a failed and a passing golden-path run.
4. `invai-infra/scripts/gate/lib.sh:218` (`write_stamp`): the SHA is read with `git rev-parse HEAD` *after* all suites finish, and nothing checks that the tree the suites ran on equals that commit (no SHA captured at start, no `git status` check).
   - **Failure scenario:** during a wave the gate takes minutes (the golden-path phase much longer). An owner commits `invai-backend` while the gate is running on the previous tree. The stamp records the new SHA, which was never tested, and the guard allows pushing it. Also, a tracked file left uncommitted (another agent's WIP that makes a failing test pass) is tested but not pushed, while HEAD is stamped as passing.
   - **Fix:** capture each repo's HEAD at start. At the end, write the stamp only if HEAD is unchanged and `git status --porcelain --untracked-files=no` was empty at start (or refuse to start on a dirty tracked tree, with a one-line reason). Otherwise print a FAIL line saying the repo changed during the run.
5. `.claude/hooks/guard-bash.py:381-387`: the stamp is compared with the local `HEAD`, not with what is being pushed. With a fresh stamp for HEAD, `git push origin <other-sha>:main` and `git push origin some-branch:main` are allowed (probe above).
   - **Failure scenario:** the tech lead pushes a colleague's local branch or a specific commit (`git push origin abc123:main`) after gating a different HEAD. Untested code reaches `main` with the guard's approval. AC5's intent is "the pushed commit passed the gate".
   - **Fix:** when a refspec is given, rev-parse its source (`git -C <root> rev-parse <src>^{commit}`) and compare that with the stamp. Or deny any explicit refspec other than `main`, `HEAD`, `HEAD:main` and `main:main`. Add both cases to `test_push_stamp.py`.

## Optional notes (not blocking)
- The stamp is a speed bump, not a boundary, as expected. Any allowed Bash command (`printf '{...}' > invai-infra/.gate/pass.json`, a Python one-liner) can forge it; `guard-paths.py` only covers Write/Edit. A git worktree named `invai-backend-*` outside the workspace reads `<its parent>/invai-infra/.gate/pass.json` (the regex allows a suffix), and that path is just as writable. `INVAI_GATE_STAMP_PATH` in the command text is ignored (probed). If it matters later, have the guard deny Bash writes to `.gate/pass.json` except from `gate.sh`.
- `pnpm gate` with backend/web/floor in scope runs `db:reset` from inside the script, so the guard's `db:reset` ask for non-QA callers doesn't fire. The port check only catches a stack on the default ports; an agent on `PORT=31xx` using the shared dev DB is wiped silently. Consider having the guard `ask` on `pnpm gate` for anyone but the main session and QA, or check for other connections to the dev DB (`invai`) before resetting. The port check also runs only at the start; after minutes of suites a stack may have started on those ports, so re-check right before the golden-path phase.
- `write_stamp` replaces the whole file, so `pnpm gate invai-backend` then `pnpm gate invai-web` drops the backend entry. This fails closed, but merging entries for repos whose HEAD is unchanged would save a re-run.
- `count_passed` prints `1 passed` for typecheck (a made-up number) and "files checked" for lint. `failing_names` uses `\s` in BSD `sed`, which doesn't strip, and `paste -sd'; '` alternates `;` and space as separators. `seed_out` captures stderr only for `db:seed` (line 100: `2>&1` binds to the last command).
- `STARTED_PIDS=("${STARTED_PIDS[@]/$dev_pid/}")` is a pattern substitution: it would change PID 1234 into `4` if 123 were removed. Harmless now (one entry), fragile if more PIDs are added.
- `invai-docs/team/hooks/guard-bash.py` (the copy the adversarial suites import) doesn't have this change. The tech lead syncs it with the tests; until then those suites don't cover the live push check.
