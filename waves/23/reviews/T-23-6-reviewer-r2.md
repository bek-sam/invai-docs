## Blocking findings
1. `.claude/hooks/guard-bash.py:440-453` (`_refspec_sources`), fed by the tokenizer at `:142-160`: `shlex` with `punctuation_chars` splits `2>&1` into `2`, `>&`, `1`, and the `2` stays in the push's word list. `_refspec_sources(["origin", "main", "2"])` returns `["main", "2"]`, `git rev-parse 2^{commit}` fails, and the push is denied.
   - **Failure scenario:** the tech lead runs `pnpm gate invai-backend`, gets all PASS and a stamp for HEAD, then pushes with the usual `git -C /Users/bekbolsun/invai/invai-backend push origin main 2>&1 | tail -3` (the shape of the team's own segment tests B06/B01, and of the 2026-09-27 lesson about pushes wrongly denied). The guard denies it with "can't resolve '2' ... Run 'pnpm gate' again before pushing". Following the message re-runs the full gate, including the dev DB reset, and the push is denied again. Reproduced for `2>&1`, `2>/dev/null`, `2> file`, with `-q`, and with `git push origin 2>&1`.
   - **Fix:** don't count a word as a refspec when it is a file-descriptor number directly before a redirect operator (drop a pure-digit word followed by `>`, `>&`, `>>`, `<` in the tokenizer, or have `_refspec_sources` ignore words that are all digits when the next token was a redirect). Add `git push origin main 2>&1 | tail -3`, `... 2>/dev/null` and `git -C <abs> push origin main 2>&1` with a fresh stamp as `allow` tests, and the same with a stale stamp as `deny`.
2. `.claude/hooks/guard-bash.py:476-477` (`if found is None: return None`), with `_push_target_dir` `:413-416` and `_advance_cwd` `:258-262`: a path that doesn't exist on disk is treated as "certainly outside any repo" and allowed. `~` is never expanded (`~/invai/invai-contracts` becomes `<cwd>/~/invai/invai-contracts`), and `{}` from `xargs -I{}` / `find -exec` is taken literally. `_find_gate_repo` walks up from the non-existent path, finds no `.git`, and the push is allowed with no stamp. This is the fail-open path round-1 finding 1 asked to close ("fail closed once the command is a push whose repo can't be pinned"): here the repo isn't pinned, it's mis-pinned.
   - **Failure scenario:** after a failed gate run (or none), the tech lead or the main session types `git -C ~/invai/invai-backend push origin main` or `cd ~/invai/invai-backend && git push origin main`. Bash expands `~`, git pushes invai-backend, and the guard allowed it without any stamp. The same happens with `ls -d invai-* | xargs -I{} git -C {} push origin main`.
   - **Fix:** expand `~` / `~user` with `os.path.expanduser` in both `_advance_cwd` and `_push_target_dir`, and treat `{}` and any resolved base that doesn't exist (`not os.path.isdir(base)`) as `CWD_AMBIGUOUS` (deny with the existing message). A real directory outside every repo (`/tmp`) still falls through, so `test_still_allows_when_genuinely_outside_any_repo` keeps passing. Add the `~`, `xargs -I{}` and `find -exec {}` forms as `deny` tests with no stamp, and `git -C ~/invai/invai-contracts push origin main` with a fresh stamp as `allow`.

## B07 and the legitimate push forms (asked by the tech lead)
- **Denying B07 is right.** The loop pushes `invai-backend`, a code repo, and the guard can't know which stamp to check for `$r`. When the tech lead syncs the mirror, B07's expectation should become `deny`, and an `allow` case for the lesson's shape should be added with literal paths (for example `git -C invai-docs push origin main; git log -1 | tr -d x`). That file is the tech lead's (`invai-docs/team/**`), as the author says.
- **Legitimate forms:** a plain `git -C /abs/repo push origin main` with a fresh matching stamp passes, and invai-docs pushes pass without a stamp in every form I tried (absolute `-C`, relative `-C`, `cd invai-docs && ...`, cwd in docs, with `2>&1 | tail`). The only legitimate form now wrongly blocked is a code-repo push with a stderr redirect (finding 1). A loop over several repos is now always denied: push them one by one with literal `-C` paths.

## Optional notes (not blocking)
- When `write_stamp` skips a repo because its tree changed during the run, it only writes a log line; stdout still shows all PASS lines and the gate exits 0. It fails closed (the push is later denied for "no gate stamp"), but a `FAIL <repo> stamp: tree changed during the run` line on stdout would save a confusing round trip.
- `--untracked-files=no` means an untracked source file that a committed file imports is tested but not pushed. I suggested that flag in round 1 because other agents' untracked WIP is common here; worth knowing when a pushed commit fails CI but passed the gate.
- The `(...)` simplification (a `cd` inside parentheses leaks out) can resolve a later push to invai-docs while bash really runs it in a code repo (probe above). It is contrived, but the fail-closed choice would be to mark the tracked cwd `CWD_AMBIGUOUS` after any `(...)` group that contains a `cd`, instead of keeping the inner directory.
