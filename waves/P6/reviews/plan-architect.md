## R1 (T-P6-2/3): re-check on the 25 s ping, `event: unauthorized`, then 401. Sound, no contract change
- **Contract: no change, and none wanted.** `ready`, `ping` and `shutdown` are transport control events written by `src/api/events.ts` and are not in `invai-contracts/src/realtime.ts` `RealtimeEvents`; `unauthorized` is the same kind. Putting it in `RealtimeEvents` would be harmful: the web subscribes to every key (`invai-web/src/lib/realtime.ts:147-148`) and routes it through `keysForEvent`, and data `""` is not a `RealtimeEnvelope`. No contract card.
- **Web (no tight loop):** native `EventSource` (`realtime.ts:143`). It listens only to `RealtimeEvents` names and `message`, so it ignores `unauthorized`. When the stream ends it reconnects once after the browser's default delay (about 3 s). The reconnect gets 401, a non-200 answer that fails the EventSource for good: `readyState` CLOSED, then `onerror` sets "closed" (`:145`). No retry loop. T-P6-2 must not write a `retry:` field on `unauthorized`.
- **C1 (blocking design gap): a transient error must not look like a revoke.** `buildContext` catches every error and returns an anonymous context (`invai-backend/src/api/context.ts:133-136`), and `isRevoked` fails open (`src/lib/ratelimit.ts:66-72`). So a DB blip during a re-check reads as "unauthorized", and every tablet in the shop would lock at once. Rule for T-P6-2: send `unauthorized` only when the re-check gives no session or a different company **and** a `select 1` probe through the db client succeeds. If the probe fails, end the stream with a retry hint and no `unauthorized`, the way the shutdown path does. Add a test for this. `context.ts` stays untouched. AC4's "decide" is answered by this rule.
- **C2 (AC2 bound):** `isStationTokenLive` caches the answer for 30 s per process (`src/modules/tenancy/floor-auth.ts:246-262`), and a revoke evicts the cache only in the process that handled it (`:126`). With one API instance, ≤ 30 s holds. With several instances the worst case is 25 + 30 = 55 s. Restate AC2 as "≤ 30 s on one instance (gate), ≤ 55 s across instances". Fixing the cache across instances is out of scope (push-based revoke is already fenced out).
- Cookie re-check hits the DB each time: there is no `cookieCache` in `src/auth.ts:255-259`, so a sign-out is seen at the next re-check. Keep the 25 s interval. Expected load is about 1 small query set per stream per 25 s.
- **Floor fallback for every case** (`onAuthFailure`, `invai-floor/src/app/actions.ts:293-297`, already tells apart a removed station, which goes to the station-removed screen, from an ended session, which goes to the PIN lock):
  - New backend, new floor: on `unauthorized` it stops and calls `onAuthFailure` once. A revoked token goes to the station-removed screen. A revoked or expired session, or a deactivated member, goes to the PIN lock. After the next PIN login the token changes and `useRealtime` (`src/hooks/useRealtime.ts:23-37`) connects again.
  - New backend, cached old floor: the old floor ignores the event name. The stream ends and the floor reconnects with the header (`sse.ts:88`). It gets 401 and calls `onAuthFailure`, which is the same screen. It keeps backing off up to 30 s until the token changes, which is harmless.
  - Old backend, new floor: the header works. A revoke is seen at the next reconnect, or at the queue poll's 401 (`useStationQueue` calls `onAuthFailure`), as today.
  - Transient DB error (with C1): a retry hint, then the floor reconnects with backoff. No sign-out.
  - 401 on connect: T-P6-3 AC2 stops retries. Recovery goes through the lock and PIN, which gives a new token. If no station is paired, it stays offline (it is unpaired).
  - Shutdown, network loss and demo mode: unchanged (demo has no SSE).
- T-P6-3: the parser dispatches `data: ""` because `data` holds one empty line (`sse.ts:28`), the same as `shutdown` today. Fine.

## R2 (T-P6-4 / B-208): the fix lives in the seed; the card's assumption is right
- Not in production batch build: `buildBatch` and `collectCandidates` (`src/modules/production/sheets.ts:201-240, 361`) correctly build what is eligible now. A live shop also has renders pending, and making the product wait on the worker would be wrong.
- Not in the gate: `invai-infra` is read-only and not pushed (OI-22). A wait in the gate also hides a hand-over that changes over time from demos and CI (`scripts/ci/run-e2e.sh` starts the worker after the seed).
- **Mechanism the owner must confirm by measurement:**
  1. The seed writes `qaStatus: "passed"` without running QA (`src/db/seed/builder.ts:548`). The released `design.updated` events (about 40) then run `runDesignQaJob` (`src/modules/catalog/jobs.ts:18-31`), which writes the real `passed`/`warn`/`failed` (`catalog/service.ts:370-383`), and `failed` drops items from the pool (`sheets.ts:173`).
  2. A personalized unit still `pending` becomes eligible only after `artwork.render_requested` runs the render job (`personalization/jobs.ts:38`; `sheets.ts:169`).
  - Both events stay held until `releaseOutbox` at `builder.ts:2318`.
- **Fix:** before `releaseOutbox`, apply those effects inline with the same service functions: `runDesignQa` for each seeded design, and `renderPendingItem` (`personalization/service.ts:631`) for pending units, each under `withTenant`, and only when imaging is up. Keep the release. The re-run on the worker is then a no-op: the artwork job's pending guard skips done units, and QA on the same file gives the same result. With imaging down, both jobs skip (`catalog/jobs.ts:24-27`), so the pool is already settled. Watch AC5's +10% run time (about 40 QA calls).
