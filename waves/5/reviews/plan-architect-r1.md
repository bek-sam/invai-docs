## Demo-company isolation and billing exclusion
Isolation is free: a demo company is an ordinary `company_id`-partitioned row, covered by the same RLS every tenant table already has. Exclusion is not free, and the plan as written treated it as a flag check when it isn't. `companies.demo` (`db/schema/tenancy.ts:62`) exists but is read in exactly one place in the whole backend (`toOrg()`, `service.ts:52`) — nothing excludes it from anything. Concretely, three real gaps, now specified in the contract-stub section:
1. **Trial expiry.** `today/org-hooks.ts`'s `onOrganizationCreated` (the generic Better Auth `organization.create` hook) inserts a 14-day trial subscription for every shop org unconditionally. `billing/service.ts`'s `expireTrials()` is a bulk, company-blind `UPDATE`. An unpatched demo company's trial expires and locks the demo two weeks after it's created.
2. **Plan limits.** `assertWithinPlan` (called from `channels.connect`, `team.invite`) needs to short-circuit for demo companies once (1) is fixed, or it'll fail closed on a company with no subscription row.
3. **Marketplace calls.** `channels/service.ts:366`: `provider = env.mocks.shopify ? "mock" : "live"` is a pure env-level decision with zero per-company check. Once real keys exist in production, a demo company clicking "connect Shopify" runs a real OAuth flow against a real store. This is the sharpest finding in this review — it's the one place "mock only" could otherwise silently fail exactly when it matters most (after go-live, not during local dev where `env.mocks` already masks the bug). Every `env.mocks.*` branch needs the same demo check, not just Shopify's.

## Seed refactor into a reusable builder
Feasible, but larger than its one bullet in T-5-3 suggests. The seed is ~2,000 lines (`db/seed/index.ts` 1,617 + `data.ts` 422) as one `main()` function, not composable units. Three concrete obstacles to "generate demo data for any company without breaking `db:seed`":
- A single module-level PRNG (`rng(20260924)`, `index.ts:76`) closed over by every random call — calling the builder twice in one process (Desert Bloom, then a demo company) needs a fresh seeded RNG per call, threaded through, not the module singleton.
- Hardcoded volumes (300 orders, 60 customers) and a Desert-Bloom-specific slug idempotency check — a smaller/faster demo variant needs these parameterized, and the idempotency check needs to key off something demo-specific (e.g. `demoOwnerUserId`), not a fixed slug.
- The raw-SQL `stock_levels` upsert (the one behind B-106's known seed/worker race) isn't obviously safe if two seed-builder calls (or a seed call + a live worker) run concurrently per company — worth a look before assuming the smaller demo path inherits the full seed's correctness for free.
Recommendation, applied to the card: scope this as "extract + parameterize, minimal new behavior" and treat `db:seed`'s unchanged output as the hard constraint it already is. If it doesn't land clean in one review round, split it into its own card next wave rather than carrying it into a second round bundled with the checklist/Today/demo-UI work — the same escape hatch wave 2 used for T-2-5.

## PIN-only members in Better Auth (a user with no email?)
Checked the installed `better-auth@1.7.5` in `node_modules`. The answer is no, not literally: `@better-auth/core`'s base `user` table hard-defines `email: { type: "string", unique: true, required: true }` with no supported override, and it's not a shadow schema — `auth.ts`'s `drizzleAdapter` points Better Auth directly at InvAI's own `users`/`members` tables (`db/schema/tenancy.ts:24-27`'s own comment confirms this), where `users.email` is additionally a real Postgres `NOT NULL UNIQUE` column. `staff_pins.userId` is a `NOT NULL` FK to `users.id`, so there's no lighter-weight staff entity to fall back to either — PIN-only staff must be a real `users` row.
The workable design (written into the contract stub): keep `User.email` required in the schema, have the backend write a synthetic, non-deliverable placeholder (`pin+<uuid>@floor.invai.internal`) via a direct Drizzle insert — bypassing `auth.api.signUpEmail` entirely, so no password and no `accounts` row get created, which is what actually blocks web sign-in, not the email field — and add a new `User.pinOnly` boolean so the web and the mailer both know never to treat that string as a real address. This is materially different from (and better than) the wave's original "accepts `pinOnly: true` with no email" framing, which isn't achievable as literally stated.

## `updateAddress` rules
Fully specified in the contract stub. Two corrections to the wave's one-liner:
- "Not yet labeled" should gate on the shipment's `LIVE_LABEL` status set (`shipping/service.ts:79`: `labeled, in_transit, delivered, exception, returned`), the same check `shipping/service.ts:1006-1008` already uses for "does this order have a live label" — not on `orders.status`, which is a derived rollup and the wrong source of truth here.
- "Re-runs address checks" has no existing implementation to reuse for a check this early: the only carrier-verified validator in the codebase, `shipping.rates`, requires the order to already be packed. The only thing that can run at hold time is the format-only heuristic already in `shipping/service.ts:482` (non-empty street1, valid zip pattern). I specified this explicitly so the card doesn't imply a carrier call that can't actually happen pre-pack.
- Persistence should reuse `orders/import.ts`'s existing `buyerPii` upsert path (`piiValues` + `updateExisting`'s address branch, `import.ts:283-360`) rather than inventing a second address-write path — `shipTo` lives in a separate `buyerPii` table gated by the `orders.manage`-only `canSeeAddress` read check (`orders/service.ts:136`), not a column on `orders` itself. This is worth calling out on its own: any engineer who greps `orders` schema for `shipTo` and finds nothing might reasonably (and wrongly) conclude it needs a new column.
