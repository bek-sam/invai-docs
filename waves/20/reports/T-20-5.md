## Built
- `pnpm db:reset` now also empties the app's five BullMQ queues (`Queue.obliterate({ force: true })` over `QUEUE_NAMES`) in the Redis DB of `REDIS_URL`, prints the per-queue count and reminds you to restart the worker so its repeatable sweeps re-register. No `FLUSHDB`, no `KEYS`; only `bull:<queue>:*` keys go. Refuses under `NODE_ENV=production`. (files: `invai-backend/src/db/reset.ts`, test `src/db/reset.test.ts`)
- The seed builder parks each phase's outbox events (`holdOutbox`: `dispatched_at` set, `last_error = "held: seeding in progress"`) inside the same transaction that emitted them, and releases them all once at the end (`releaseOutbox`, only rows carrying the marker), so a running worker's relay never dispatches jobs for a half-built company. (files: `src/db/seed/outbox-hold.ts` + test, `src/db/seed/builder.ts`)
- `SEED_OUTPUT_FILE=<path>` redirects the seed's output JSON, so seeding a DB copy never overwrites the shared `seed-output.json`. (file: `src/db/seed/index.ts`)
- Docs: `invai-backend/README.md` (reset/seed behaviour), `src/modules/README.md` (bulk-builder hold pattern under the job pattern).

## Root cause (AC1: "document the cause you found")
The seed builder commits phase by phase (blanks → designs → orders in batches of 20 → sheets → shipments → inventory → usage/ad spend) and every phase goes through the real services, so each phase leaves real `outbox_events` rows. With a worker running, its relay dispatches them within a second and the subscribers write **derived rows for the half-built company** while later seed phases still insert the same natural keys plainly:

| Event emitted mid-seed | Subscriber (module) | Derived row it writes | Seed phase that later collides |
|---|---|---|---|
| `sheet.built` | `billing.recordSheetBuilt` | `usage` upsert on `(company_id, period)` | plain `tx.insert(usage)` at the end of the build (`builder.ts:1588`) → **unique violation `usage_company_id_period_index`** |
| `order.cancelled` (with scrapped transfers) | `production.scrapCancelled` | scrap `inventory_movements` + `stock_levels` upsert | inventory phase aggregates movements into `stock_levels` (`builder.ts:~1481`); its own upsert was already `ON CONFLICT` since T-5-3, which is why the gate saw `stock_levels` in wave 19's earlier seed and `usage` afterwards |
| `item.state_changed`, `shipment.labeled` | `finance.recompute` | profit lines for orders whose items were still being inserted | recomputed later, but wasted work and transient state |

Fix: hold the events per phase and release them once at the end (release order is `created_at`, exactly what a worker started after the seed has always seen). The alternative, making every seed insert an upsert, would hide the real problem (jobs acting on an unfinished tenant) and would keep the derived rows racing the seed's own numbers.

## Decisions
- Hold/release the outbox per phase inside the seed rather than pausing the relay or upserting every seed row: the seed stays a real-service run, the worker needs no seed-awareness, and only rows carrying the `held:` marker are ever released (a parked-for-good row with another `last_error` is never touched). Card-local, no ADR.
- `obliterate({ force: true })` rather than `drain()`: `drain` leaves active, completed, failed and repeatable records, which is exactly what replayed after the wave 19 reset. Per architect A2.
- `SEED_OUTPUT_FILE` env instead of a CLI flag: the seed already takes everything from env (`DATABASE_URL`, `REDIS_URL`), and the brief's rule "never write `seed-output.json`" needs an override that works for `pnpm db:seed` unchanged.

### Blocking finding 1: the seed's plain `alerts` inserts collide with the worker's scheduled sweeps
Fixed in `invai-backend/src/db/seed/builder.ts` (one commit on top of 8fdc733, see `git log -1 -- src/db/seed/builder.ts`):
- `stock_low` and `order_at_risk` alerts go through `upsertAlerts` (`ON CONFLICT (company_id, dedupe_key) DO UPDATE`, status back to `open`, the seed's text and severity win). Same keys the sweep uses (`stock_low:<variant>`, `order_at_risk:<order>`), so nothing is hidden: the row a plain insert would have written is what ends up there.
- `inventory_settings` is `ON CONFLICT DO NOTHING` (defaults only; the sweep's `loadSettings` creates the row lazily). This is the **first** collision on the base code, before the alerts one.
- The period's `usage` row is `ON CONFLICT (company_id, period) DO UPDATE`, counted from the DB (orders and labels of the period), so an early `recordUsage` (a mock poll import or an AI credit spend) never leaves a second row or stale numbers.

**Root cause, complete (AC1 "document the cause"):** two paths, not one. (1) Outbox: subscribers of the seed's own events (`sheet.built` → `usage`, `order.cancelled` → scrap movements) — fixed in r1 by holding each phase's events. (2) Scheduled sweeps registered with `upsertJobScheduler` by both API and worker: they don't go through the outbox, `every`-schedulers fire at registration and every tick, and they fan out to every `type = 'shop'` company, the half-built one included. Fixed here by making every seed row a sweep can also create an upsert.
