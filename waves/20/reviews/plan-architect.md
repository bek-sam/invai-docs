## Verdict: approve with changes

## Required changes

**A1 — Ownership glob overlap, T-20-3 vs QA-acceptance.**
`wave.md`'s own "Order and ownership" table grants T-20-3 exclusive ownership of "new `invai-backend/src/**/*.acceptance.test.ts` files" (also on `T-20-3.md`'s "Owned paths"), while the same table grants "QA acceptance" exclusive ownership of `invai-backend/src/modules/{digest,market,today}/*.acceptance.test.ts`. T-20-3's glob is a superset that literally includes QA-acceptance's files. T-20-3's listed examples (shipping, easypost-live, shopify-live, ss-live, ai/publish, personalization/render) don't touch digest/market/today, so intent is clear, but the written grant is not exclusive as claimed. Fix: scope T-20-3's owned-paths glob to exclude `src/modules/{digest,market,today}/**` (e.g. list the actual target files/dirs instead of `src/**/*.acceptance.test.ts`).

**A2 — T-20-5's Redis-drain verification doesn't prove the "other prefixes" half of AC2.**
The same `redis` client (`invai-backend/src/lib/queues.ts:17`) backs BullMQ (default prefix `bull:`), the rate limiter (`src/lib/ratelimit.ts`: `rl:`, `revoked:`, `ba-rl:` keys) and realtime SSE (`src/lib/realtime.ts`: Redis Streams + pub/sub), all in the same DB index. AC2 correctly requires the reset "never flushes other Redis DBs or other prefixes," but T-20-5's Verification only checks cross-DB isolation ("DB 13/15 untouched") — a `FLUSHDB`/`redis.keys('*')`-based implementation on DB 14 would pass that test while wiping `rl:`/`ba-rl:`/realtime-stream keys on the *same* DB, silently violating AC2's other-prefix clause. Fix: add a same-DB, non-bull sentinel key (e.g. set an `rl:`-prefixed test key on DB 14 before reset) and assert it survives, alongside the DB-13/15 check. (The correct mechanism is per-queue `Queue.obliterate()` over the existing `QUEUE_NAMES` list from `queues.ts`, read-only for T-20-5 — no ownership conflict there.)

**A3 — T-20-1 ↔ T-20-2 sequencing gap.**
`T-20-2.md` "Depends on" says: "grep T-20-1's `render.ts` output keys against your copy" before finishing. But `wave.md`'s Order and ownership puts T-20-1 and T-20-2 in the *same* batch 2, run concurrently, with no named handoff commit (unlike QA-acceptance, whose commit is explicitly the sync point for both cards). As written, T-20-2 could finish and grep against a `render.ts` that hasn't landed T-20-1's wording-rule changes yet. Fix: either (a) sequence T-20-2 to start only after T-20-1's commit lands (name it in `wave.md` the way QA-acceptance's commit is named), or (b) drop the grep dependency — both cards already get the identical wording rule verbatim from `wave.md`, which is the real sync mechanism, and T-20-1's `render.ts` (email-only templates) isn't actually what T-20-2 consumes at runtime (web reads `DigestFact.formatted`/`DigestGlanceItem`, not the backend's email `TEMPLATES`).

**A4 — AC3's "points" fix needs a sharper acceptance test, not just relabeling.**
`invai-backend/src/modules/digest/build.ts:42-59` (`glanceOf`/`row()`) currently computes `changePct` for **every** glance metric, including `marginPct`/`onTimeRate`, via `pctChange(cur, prev)` — a *relative* percent change of the value itself. That is exactly wave-19 gate issue 3 ("Margin: 33.4% (+26% vs last week)" for a 26.5→33.4 point move). AC3's target ("+6.9 pts") requires switching those two metrics to an absolute point-difference (`cur - prev`), not just relabeling the existing (still relative) number with "pts". Neither T-20-1's card nor `QA-acceptance.md` spells this out explicitly. Fix: `QA-acceptance.md`'s fixture should pick margin/on-time before/after values where relative-% and point-diff produce visibly different numbers (e.g. margin 26.5 → 33.4 gives "+26%" if mislabeled, "+6.9 pts" if correct), so a superficial fix can't pass. Not blocking the wire shape — no contract change needed either way, since `DigestFact.formatted` is a free string.
